# Moving to a new machine

Windows to Windows. The repo rebuilds the harness; this guide covers everything
the repo **cannot** rebuild.

Split it this way and nothing gets lost:

| | Rebuilt from | Action |
|---|---|---|
| skills, agents, commands, hooks, rules, scripts, `settings.json` | this repo | `setup-windows.ps1` |
| MCP server registration | this repo | `setup-windows.ps1` (writes `~/.claude.json`) |
| MemPalace drawers, per-project memory, Obsidian vault, SSH keys, Zotero library, `.env` | **nothing** | copy by hand |
| project code | GitHub | `git clone` -- **but uncommitted work is not on GitHub** |
| unversioned project folders | **nothing** | copy by hand |

## TL;DR

```powershell
# --- old laptop ---
cd $HOME\claude-brainlab
git pull; git status                 # commit anything outstanding
powershell -ExecutionPolicy Bypass -File install\backup-for-migration.ps1 -Destination E:\claude-migration

# --- new laptop ---
git clone https://github.com/Karakurtt/claude-brainlab.git $HOME\claude-brainlab
cd $HOME\claude-brainlab
powershell -ExecutionPolicy Bypass -File install\setup-windows.ps1
# then restore the payload (see "Restore" below) and restart Claude Code
```

## 1. Before you leave the old laptop

### Audit first, copy second

```powershell
powershell -ExecutionPolicy Bypass -File install\backup-for-migration.ps1 -Destination E:\claude-migration -AuditOnly
```

`-AuditOnly` copies nothing and prints what it would take, plus a warning per
project that has **uncommitted changes, unpushed commits, stashes, or no git
remote at all**. Work in any of those states does not exist on GitHub and a
fresh clone on the new machine will not have it.

Clear the warnings you care about (commit and push), then drop `-AuditOnly` to
copy for real. The script writes `MIGRATION-MANIFEST.txt` listing every asset
and every remaining warning.

### What gets copied

| Asset | Size | Why it cannot be rebuilt |
|---|---|---|
| `~/.mempalace/` | ~15 MB | 1883 drawers of cross-session memory |
| `~/.claude/projects/*/memory/` | small | per-project memory files |
| `~/.ssh/` | 30 KB | config + 5 private keys; not reissuable |
| `~/Zotero/` | ~65 MB | the literature library `paper-ingest` writes into |
| Obsidian vault | small | path is read from `.env` |
| `claude-brainlab/.env` | tiny | gitignored; holds the Zotero API key |
| unversioned project folders | varies | no remote, no backup |
| `graphify-out/graph.json` + report | ~1 MB each | LLM extraction is not free; `cache/` is dropped |

Add `-IncludeTranscripts` to also carry `~/.claude/projects` session
transcripts (~100 MB). Useful history, not required for anything to work.

### Things the script deliberately does not touch

- **`~/.claude/` components** -- reinstalled from the repo. Copying the old one
  over the new install re-introduces any drift you just cleaned up.
- **`~/.claude.json`** -- regenerated by `setup-windows.ps1`. It also contains
  machine-local session state; carrying it over is not worth it.
- **`graphify-out/cache/`** -- regenerable, and 195 MB of MoEEdit's 263 MB.

## 2. The one trap: memory is keyed by path

Per-project memory lives in `~/.claude/projects/<key>/memory/`, where `<key>`
is the project's **full path with every non-alphanumeric character replaced by
a dash** -- one dash per character, including each letter of a non-Latin
username:

```
C:\Users\Roman\MoEEdit   ->   C--Users-Roman-MoEEdit
C:\Users\Роман\MoEEdit   ->   C--Users-------MoEEdit     <- current keys
```

The current username is Cyrillic, so it encodes to five dashes and the keys
carry no readable username at all. **If the new laptop's Windows user is
created with a Latin name -- likely, and otherwise a good idea -- every key
changes and all per-project memory silently stops loading.** No error; the
files just never match.

Either keep the identical username and project layout, or rename the copied
directories before restoring. Preview first:

```powershell
$M   = 'E:\claude-migration\claude-projects'
$old = 'C:\Users\Роман'                       # the OLD home path
$enc = { param($s) ($s -replace '[^A-Za-z0-9]', '-') }
$oldP = & $enc $old
$newP = & $enc $HOME

Get-ChildItem $M -Directory | Where-Object { $_.Name.StartsWith($oldP) } | ForEach-Object {
    $new = $newP + $_.Name.Substring($oldP.Length)
    "{0}  ->  {1}" -f $_.Name, $new
    # Rename-Item $_.FullName $new      # uncomment once the preview looks right
}
```

Then verify for real: open a session in a migrated project and confirm its
`MEMORY.md` entries show up in context. An empty memory section means the key
is still wrong.

The same encoding applies to the project folder name, so keep those identical
too (`biology_submission` encodes to `biology-submission`; renaming the folder
to `biology-submission` would *not* collide, but any other rename breaks the key).

## 3. On the new laptop

### Prerequisites

```powershell
winget install Git.Git OpenJS.NodeJS.LTS Python.Python.3.12 astral-sh.uv
```

Then the tools that ship their own MCP servers and skills:

```powershell
uv tool install mempalace             # mempalace-mcp.exe
uv tool install zotero-mcp-server     # zotero-mcp.exe
uv tool install graphifyy             # graphify.exe
graphify install --platform claude    # writes ~/.claude/skills/graphify
```

`graphify` is third-party and ships its own skill, so it is **not** vendored in
this repo -- it must be installed separately or `/graphify` will not exist.
Install Zotero 7 and Obsidian from their own installers.

### `.env` gained keys after the upstream merge

The old `.env` predates the fork sync and is missing five keys. Carrying it over
verbatim silently skips two MCP servers:

| Key | Effect if absent |
|---|---|
| `LAB_MCP_URL`, `LAB_MCP_TOKEN` | `lab-knowledge` is not registered -- no shared research base |
| `PLANE_API_KEY`, `PLANE_WORKSPACE_SLUG`, `PLANE_BASE_URL` | `plane` is not registered |

Both are all-or-nothing, and the installer prints a `[skip]` line for each, so
check the install output rather than assuming. The lab token comes with BRAIn
Lab team membership -- see the README. Everything else works without them.

Copy the missing keys from `.env.example` and fill what you have.

### Install the harness

```powershell
git clone https://github.com/Karakurtt/claude-brainlab.git $HOME\claude-brainlab
cd $HOME\claude-brainlab
powershell -ExecutionPolicy Bypass -File install\setup-windows.ps1
```

The installer prompts for paths and writes `.env` -- or skip the prompts by
restoring the old `.env` first (see below) and re-running. Details of what it
does: [`WINDOWS.md`](WINDOWS.md).

### Restore

```powershell
$M = 'E:\claude-migration'
Copy-Item "$M\mempalace\*"       "$HOME\.mempalace"   -Recurse -Force
Copy-Item "$M\ssh\*"             "$HOME\.ssh"         -Recurse -Force
Copy-Item "$M\Zotero\*"          "$HOME\Zotero"       -Recurse -Force
Copy-Item "$M\claude-projects\*" "$HOME\.claude\projects" -Recurse -Force
Copy-Item "$M\claude-brainlab.env" "$HOME\claude-brainlab\.env" -Force
# vault and unversioned projects: put them where .env says they live
Copy-Item "$M\vault\*"           "$HOME\Documents\my-vault" -Recurse -Force
Copy-Item "$M\unversioned\*"     "$HOME" -Recurse -Force
```

Then fix SSH key permissions -- OpenSSH refuses keys that are group/world
readable, and a plain copy will not carry the old ACL:

```powershell
Get-ChildItem "$HOME\.ssh" -File | Where-Object { $_.Name -notmatch '\.(pub|bak.*)$' } | ForEach-Object {
    icacls $_.FullName /inheritance:r /grant:r "$($env:USERNAME):(R)" | Out-Null
}
```

Re-run `install\setup-windows.ps1` after restoring `.env` so placeholders expand
to the restored paths.

### Clone the projects

Each has a GitHub remote; clone into `C:\Users\<you>\` to keep memory keys
stable. Then re-apply any uncommitted work the audit warned about.

## 4. Verify

```powershell
claude mcp list           # mempalace + zotero: "Connected"
```

In a **new** session (MCP tools only load at session start):

| Check | Expected |
|---|---|
| ask for `mempalace_status` | 1883-ish drawers, wings listed |
| ask for `zotero_get_collections` | real collections (Zotero must be running) |
| `/graphify` | skill resolves |
| open a project, check its memory | its `MEMORY.md` entries appear in context |
| `Get-Content $HOME\.claude\CLAUDE.md \| Select-String 'vault root'` | a real path, **not** `${OBSIDIAN_VAULT}` |
| `ssh h200 nvidia-smi` | GPUs listed |

That last `CLAUDE.md` check matters: before the fix in `b050fb7` the installer
never expanded placeholders in `CLAUDE.md`, so on a **fresh** machine (where the
installer writes `CLAUDE.md` rather than the `CLAUDE.brainlab.md` sidecar) every
Obsidian-routed skill was pointed at a literal `${OBSIDIAN_VAULT}`.

Zotero semantic search starts empty; rebuild the index once:

```powershell
& "$HOME\.local\bin\zotero-mcp.exe" update-db
```

### MemPalace: one writer at a time

**Root cause, found 2026-09-15: several MemPalace MCP servers were running at
once**, one per Claude Code session, all writing the same Chroma directory:

```
ProcessId  Started              Cmd
    32772  15.09.2026 12:05:50  mempalace-mcp.exe
    27388  15.09.2026 12:40:29  mempalace-mcp.exe     <- second session
```

Chroma's HNSW index is not safe for concurrent writers across processes, so
every few writes a compaction loses the segment. That is the mechanism behind
all the `*.corrupt-<timestamp>/` directories in `palace/` (2026-07-17,
2026-08-27, and twice on 2026-09-15). It is not a one-off to repair and forget:
it recurs as long as two sessions are open.

Mitigation, in order of preference:

1. Keep **one** Claude Code session with MemPalace active at a time. This is the
   only thing that removes the cause.
2. `mempalace daemon start` gives a single shared writer instead of one server
   per session (it was not running on the old laptop -- worth setting up on the
   new one).
3. Repair when it happens (below).

Note the failure mode is confusing in a specific way: **a write that reports
`Error in compaction: Failed to apply logs to the hnsw segment writer` has
usually still succeeded.** The row commits to SQLite and the drawer is
searchable; only the index flush failed. Check with a search before re-filing
anything, or you will store it twice.

### Checking index health

Corruption fails **quietly**: the drawers are all still there in SQLite and
`mempalace_status` reports a healthy count, but the vector index is left
holding a handful of elements and semantic search silently degrades to BM25
keyword matching. The giveaway is in a search result:

```
"fallback": "bm25_only_via_sqlite",
"vector_disabled_reason": "HNSW index holds 4 elements but sqlite has 1,886 embeddings ..."
```

A healthy result instead carries real `similarity` / `distance` numbers and
`"matched_via": "drawer"`.

Fix — note it takes a lock, so **no Claude Code session may be running** (its
MCP server holds the palace):

```powershell
Get-Process mempalace-mcp -ErrorAction SilentlyContinue | Stop-Process -Force
& "$HOME\.local\bin\mempalace.exe" repair --yes
```

It extracts every drawer, backs the palace up to `~/.mempalace/palace.backup`,
rebuilds the collection and the FTS5 index, then VACUUMs. Quarantined bad
segments accumulate as `palace/*.corrupt-<timestamp>/` directories; they are a
few hundred KB in total and safe to carry or delete.

Worth running once on the old laptop before copying, so the new machine starts
from a healthy palace.

## 5. Audit the harness before reinstalling

`~/.claude` drifts from this repo in both directions: tools write into
`~/.claude/skills` directly, and edits to a live skill never flow back. A
reinstall silently reverts anything that drifted forward.

```bash
cd ~ && for d in skills agents commands hooks rules scripts; do
  comm -13 <(ls claude-brainlab/$d | sort) <(ls .claude/$d | sort)
  diff -rq claude-brainlab/$d .claude/$d | grep -v '^Only in claude-brainlab'
done
```

Two kinds of output are **expected, not drift**:

- files differing only because `${OBSIDIAN_VAULT}` / `${VAULT_NAME}` were
  expanded at install time;
- `graphify`, which is installed by its own pip package.

Anything else is real: backport it into the repo and commit before reinstalling.
The 2026-09-15 audit found `obsidian-project-memory/scripts/project_kb.py` 69
lines ahead of the repo this way.

### Superseded skills the installer will not remove

The upstream merge deliberately retired six components as duplicates, but the
installer only copies -- it never deletes. So they are **still sitting in
`~/.claude` on the old laptop** and will keep being offered alongside their
replacements, which is exactly the confusion the removal was meant to end. A
fresh install on the new machine simply will not have them, which is the
correct state.

| Retired | Use instead |
|---|---|
| `skills/paper-self-review` | `skills/astar-paper-review` |
| `agents/rebuttal-writer.md` | `skills/review-response` |
| `skills/post-acceptance` | `skills/presentation` |
| `commands/poster.md`, `presentation.md`, `promote.md` | the `presentation` skill directly |

Nothing is lost in capability -- each replacement is the lab-written version
that supersedes an inherited one. To tidy the old laptop before copying:

```powershell
$stale = 'skills\paper-self-review','skills\post-acceptance','agents\rebuttal-writer.md',
         'commands\poster.md','commands\presentation.md','commands\promote.md'
$stale | ForEach-Object { Join-Path $HOME ".claude\$_" } | Where-Object { Test-Path $_ }
# review that list, then re-run with: | Remove-Item -Recurse -Force
```

## 6. Decide while you are at it

Two inconsistencies in the current setup, carried forward as-is. Worth
resolving on the new machine rather than reproducing:

- **Vault layout vs routing config.** `obsidian-projects.json` maps project
  roots to vault folders `Papers/`, `Projects/`, `Staff/`, and `.env` points
  those roots at `~/Documents/{Papers,Projects,Staff}` -- all three are empty.
  The vault actually uses `Research/` and `Teaching/`, and all real projects
  live directly in `C:\Users\<you>\`. Meanwhile `CLAUDE.md` says *never write to
  `Research/`* -- which is where the moeedit and reasoning_fallback notes are.
  Either move the notes into `Papers/` and put projects under
  `~/Documents/Papers/`, or update `CLAUDE.md` and `.env` to match the layout
  you actually use.
- **`servers.md` path.** `rules/disabled/ssh-servers.md` refers to both
  `<vault>/general/servers.md` and `<vault>/general/Knowledge/servers.md`. The
  real file is the second.
