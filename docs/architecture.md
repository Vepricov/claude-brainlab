# База знания лаборатории: как это устроено

Описание окружения, а не научного содержания. Всё, что здесь написано, проверено на живой
установке 30-09-2026; числа — замеренные, не оценённые.

## Одно правило, из которого следует остальное

**Знание живёт в git.** Не в базе данных, не в памяти службы, не в интерфейсе. Репозиторий
на каждое научное направление, внутри — размеченные markdown-страницы. Всё прочее (служба
MCP, проверки, веб, боты) — надстройки, которые читают этот git и пишут в него.

Из этого правила выводятся все остальные решения, и нарушения его обходятся дорого.
30-09-2026 замер показал, чем именно: запись, сделанная через службу мимо git, принималась,
отдавала код и исчезала при первом же чужом слиянии — 149 утверждений прочитано из git, 150
сразу после прямой записи, 149 после перечитывания. Теперь любой такой путь отвечает
отказом, а не тишиной.

## Дерево

```
база
└── тема — репозиторий git, одна на научное направление
    ├── README.md                     предмет направления, список работ
    ├── literature/<ключ>.md          разбор статьи, общий для всей лаборатории
    └── <работа>/                     папка: одна статья или одно исследование
        ├── README.md                 чем работа занята
        └── claims/<H-код>/           УТВЕРЖДЕНИЕ — это папка
            ├── README.md             что утверждаем и чем это опровергается
            ├── runs/<E-код>.md       прогон: настройки, числа, где их проверить
            ├── series/<S-код>.md     серия: что проверяли группой прогонов и что вышло
            ├── theory/<D-код>.md     выкладка с доказательством
            └── figures/<F-код>.svg   рисунок
```

Коды — ярлыки, а не адреса: `H-` утверждение, `E-` прогон, `S-` серия, `D-` выкладка,
`F-` рисунок, `R-` измерение (живёт внутри страницы прогона). Номера сквозные внутри
работы и при перенумерации меняются, поэтому в межмашинных ссылках используется UUID или
путь к файлу, а не код.

**Всё стоит на утверждении.** Прогон сам по себе не знание: он опора под утверждением,
которое проверяет. Новые прогоны на новом масштабе почти никогда не новое утверждение —
это ещё одна опора под существующим. Сущностей рядом с утверждениями не заводят.

Размер на 30-09-2026: 26 репозиториев, 33 работы, 149 утверждений, 319 серий, 923 прогона,
790 измерений, 193 выкладки, 646 разобранных статей, 186 определённых внутренних имён.

## Части и где они работают

| часть | что делает | где |
|---|---|---|
| GitLab | сам git: репозитории, ветки, предложения о слиянии, права, вердикты проверок, доски | сервер лаборатории, rootless podman |
| `pr_watch` | проверки базы: ставит галочку и пишет разбор в каждый pull request | тот же сервер, проход раз в минуту |
| `git_sync` | вносит слитые предложения в модель | тот же сервер |
| бот доступа | заявки, ключи, учётные записи на сайте, членство в команде чтения | отдельная машина, ssh до сервера лаборатории |
| обратный туннель | публичное лицо сайта и MCP наружу | сервер лаборатории, systemd с перезапуском |
| `scripts/lab` | помощник участника: клон в папку проекта, pull request, чтение проверок | машина участника |

Сайт и служба читают **одно и то же дерево**. Поэтому слияние pull request в браузере и
есть запись в базу: служба сверяется с git перед каждым обращением и видит изменение сразу,
без перезапуска.

## Кто есть кто: две личности одного человека

Доступ к базе и вход на сайт — **разные системы**, и это чаще всего путает.

- В базе человек опознаётся телеграм-идентификатором и ключом `Bearer`.
- Сайт — это GitLab, отдельная программа со своей учётной записью, про телеграм не знающая.

Мост между ними — почта: у учётной записи на сайте она та же, что у человека в базе. Бот
заводит и то и другое одним ходом и присылает всё сразу: ключ MCP, логин и временный пароль
для сайта, отдельный ключ для git, и добавляет человека в команду чтения.

**Право живёт в ключе, а не в учётной записи.** Ключ агента и ключ человека — разные ключи
на одной учётной записи, и ворота смотрят именно на ключ. Иначе агент с личным ключом
хозяина проходит любые ворота как человек.

| | человек | его агент |
|---|---|---|
| читать | да | да |
| предложить правку (pull request) | да | да, это его единственный путь |
| записать напрямую | **нет** | нет |
| одобрить и слить | да | никогда |
| завести свою работу | да | да |
| позвать человека в работу | да, если ведущий её | нет |

Видимость работы задаётся полем `visibility` в шапке её README: `members` (участники работы
и её темы), `lab` (вся лаборатория), `public`. Право читать и право писать — разные
проверки: чтобы предложить правку в чужую работу, нужно членство в ней.

## Как знание попадает в базу

```
клон у себя → ветка claim/<H-код> → правка файлов → push
           → pull request → проверки → человек сливает → запись
```

**Это единственный путь, и он одинаков для человека и для агента.** Сливать может только
человек; слияние и есть запись. Ворота стоят не на содержании правки, а на том, что она
попадает в ветку, а не в основную.

Клон живёт **в папке проекта** — там, где работает агент, а не в общем каталоге. Общая
папка на все проекты кончилась предсказуемо: агент в папке своей работы базы не видел
вовсе, а потом склонировал её из чужого локального клона, и push уходил в никуда, выглядя
успешным. Хук начала сессии заводит клон при первом заходе, обновляет при каждом и правит
адрес `origin`, если тот смотрит не туда.

Один pull request на утверждение, ветка `claim/<H-код>`. Следующая правка того же
утверждения доливает коммит в тот же pull request: человек читает одно дело целиком, а не
двадцать несвязанных строк.

Форма страницы никем не предписана. Требования есть к содержанию, не к разметке: у
утверждения должен быть достижимый критерий опровержения, у числа — адрес, по которому его
можно открыть, у нового утверждения — механизм и условия, при которых оно заявлено.

## Проверки

На каждый push встаёт галочка и приходит разбор в обсуждение pull request. Проверки одни на
любую правку: писать их к своему коммиту не нужно.

- **дерево** — прогон лежит в серии, у серии есть вердикт, у утверждения есть чем его
  опровергнуть, коды не повторяются;
- **числа** — каждое число на странице утверждения и серии встречается в прогонах под ними.
  Вывод пересказывает опору, а не добавляет к ней цифры;
- **удаления** — исчезнувшая запись названа в теле pull request.

Проверка судит **правку, а не работу целиком**: старый долг работы не мешает записать новый
прогон. Замечанием становится только то, чего не было в основной ветке.

Два правила, за которые заплачено отдельно:

1. **Число в формуле читается несимметрично.** На странице вывода число в формуле — условие
   теоремы или граница промежутка, и требовать для него прогон значит запрещать теорему. В
   прогоне формула — способ записи измеренного, и не прочесть её значит объявить ту же
   величину на странице утверждения выдуманной.
2. **Число, написанное слитно с буквами, — часть имени, а не измерение.** `H200`,
   `A100-80GB`, `RTX-2080Ti`, `LLaMA-124M`, `bs256` не требуют прогона. Измерение от
   единицы отделяют пробелом: `12 GB` читается, `12GB` нет. Цена послабления названа
   сознательно: ложные обвинения дороже пропущенной величины. Правило однажды потерялось
   вместе с модулем, в котором жило, и вернулось только потому, что тест на него оказался
   сломан молча.

## Прогон записывает код, а не человек

Гиперпараметры, числа, коммит и железо знает только код, который считал. Он их и
записывает. В обучающий репозиторий кладётся один файл `lab_run.py` (только стандартная
библиотека, python 3.9+):

```python
from lab_run import LabRun

with LabRun(work="small-vocab", name="vocab8k-seed0", settings=vars(args)) as run:
    for step, batch in enumerate(loader):
        run.metric("train/loss", train_step(batch), step=step)
    run.metric("val/ppl", ppl, step=step, final=True)
    run.where("host:~/runs/vocab8k-seed0/train.log")
```

Ложится `lab-runs/<имя>.json` с настройками, метриками, версией torch, картой, номером
задачи планировщика, коммитом и признаком грязного дерева. Падение не теряется: нехватка
памяти закрывает запись статусом `failed` с причиной.

Дальше файл отправляется вызовом `submit_run`, где называют только утверждение и серию. Ни
числа, ни настройки задать снаружи нельзя: число, прошедшее через языковую модель, проверить
уже невозможно.

## Литература

Разборы статей лежат в `literature/` каждой темы и правятся **без pull request**, прямо в
основной ветке. Ограничение не на доверии: за пределы `literature/` такая правка не проходит
самим git, через список незащищённых путей в настройке ветки. Проверяются ключ цитирования,
разметка, наличие разделов разбора и отсутствие личных путей в ссылках.

Служба вернётся, когда к базе прикрутят поиск; тогда у неё будет версия, знающая про git.
Пока агент знает только репозиторий.

## Что измерено про сам конвейер

Пять замеров про наши же инструменты. Они жили утверждениями в работах `lab-agents` и
`lab-knowledge-pipeline`, но утверждение — форма для научного вопроса, а не для инженерного
факта про свой конвейер, поэтому 07-10-2026 обе работы сняты, а измеренное перенесено сюда.
История замеров осталась в git тех репозиториев.

**Задержку прежнего поиска определяла не модель.** Расчёт вектора запроса занимал 0.03 с из
8.5 с ответа, то есть меньше процента. Правки обвязки сократили одиночный ответ с 8.5 до
2.5 с, а три одновременных запроса с 12.5 до 3.3 с, при неизменной модели. На запрос читалось
4000 векторов кандидатов. Раздельный вклад очереди и выемки векторов не измерен. Профиль
живого пути, снятый позже на другой версии поиска, показал, что бóльшую часть времени занимал
уже кросс-энкодер, то есть тоже модель: широко читать это как «модель не определяет задержку»
нельзя. Поиск выключен, повторить замер не на чем.

**Кросс-энкодер судил по началу карточки, а не по смыслу.** Окно 400 знаков; расширение до
1200 не помогло. Решающая проверка: ту же фразу перенесли с первого места на третье, не меняя
слов, — и выигрыш исчез целиком, места в выдаче вернулись к исходным (5, 8, 12 → 4, 6, 8 →
снова 5, 8, 12). Отсюда следствие, которое важнее самого замера: переписывание карточек это
подгонка индекса под одну модель, оно не переносится и ломается при её смене. Проверено на
одной статье и трёх формулировках, которые видел автор правки, то есть на удержанной выборке
не проверено.

**Сквозная проверка дерева находит то, чего сторож на записи не видит.** На `dykaf` при
полностью зелёных сторожах записи проход по дереву дал 37 замечаний, после починки 2; на
`zo-jaguar`, которую конвейер не обрабатывал, 4 замечания одного класса. Осторожная читка
важнее разницы в девять раз: большая часть находок на `dykaf` это след самих проходов, потому
что ссылки, рисунки и формулы появляются там, где страницы пишет агент. Значит сквозная
проверка нужна прежде всего как страховка проходов, а не как мерка запущенности корпуса.

**Результаты работы лежат вне базы, пока их туда не перенесёт отдельный проход.** Числа
живут в логе на сервере и в таблице рукописи, и между этими двумя местами и базой нет
ничего, что переносило бы одно в другое. В рукописи `zo-jaguar` 14 таблиц, живых 7. Это не
доказанное утверждение, а наблюдение: итог переноса в записи не сохранён.

**Видимость объекта и доступ к его содержимому независимы.** Пока объект невидим, у него нет
страницы, а значит нет и места под встроенную кнопку заявки на доступ: приходится строить
обход снаружи. Два таких обхода (ссылка в мессенджер и список участников, отрисованный
текстом на соседней странице) были построены и выброшены в тот же день, когда разделение
обнаружилось. Из независимости не следует ступень «состоит, но не читает»: наоборот, от
видимости объекта зависит, какая ступень членства уже считается читателем, и это приходится
знать отдельно для каждой настройки.

## Чего здесь нет

**Это раздел про прошлое.** Он написан про Gitea и перестал быть правдой 01-10-2026: база
переехала на GitLab, и всё перечисленное ниже там есть. Раздел оставлен как причина переезда,
а не как описание сегодняшнего дня.

- **состава участников почти нет** — членство в работах заполнено у единиц, и до переезда
  заполняется вручную;
- **нет досок задач**, доступных агенту: у Gitea в описании API нет ни одного пути про
  доски;
- **нет дерева групп**: направление → тема → работа. У Gitea одна плоская организация, в
  описании её API 34 пути про организации и ни одного про вложенность;
- **нет заявки на доступ**: кнопки «хочу в этот проект» в Gitea не существует, проверено по
  её собственному бинарнику;
- **предложения живут в памяти службы**, а не в git: перезапуск их забывает, и ветка
  помнит честнее, чем служба.

Первые четыре пункта — причина переезда на GitLab. План: [gitlab-migration.md](gitlab-migration.md).

## Как это разворачивается

Настройки, которые определяют поведение, без значений:

```
LAB_KNOWLEDGE_STORE=git          хранилище: git, а не база данных
LAB_KNOWLEDGE_GIT_ROOT           каталог с голыми репозиториями
LAB_KNOWLEDGE_GIT_URL            адрес GitLab для службы (петля 9080)
LAB_KNOWLEDGE_GIT_KIND           gitlab или gitea: какой сервер держит git
LAB_KNOWLEDGE_GIT_PUBLIC_URL     публичное лицо: адреса наружу переводятся в него
LAB_KNOWLEDGE_GIT_USERS          карта «логин на сайте → почта в базе»
LAB_KNOWLEDGE_USERS              файл доступа: люди, ключи, членство (права 600)
```

Ключи и адреса в этом репозитории не печатаются: репозиторий открытый, база — нет. Адрес
базы приходит участнику в сообщении бота и запоминается на его машине в файле с правами 600.

Карта «логин → почта» обязательна: без строки в ней слитый pull request молча не применяется
к модели, и это выглядит как потерянная правка.
