# Как база ляжет на GitLab

Раскладка, а не пожелания: что чем становится, почему именно так, и чем каждое решение
оправдано в сегодняшней работе. Читать вместе с [gitlab-migration.md](gitlab-migration.md),
где порядок работ и риски.

## Главное решение: работа становится проектом

Сегодня тема — репозиторий, а работа — папка внутри него. На GitLab работа становится
**отдельным проектом**, а тема — подгруппой. Это не косметика: из этого следует всё
остальное.

```
brainlab/                         группа лаборатории
├── <направление>/                подгруппа: 5–6 штук, названия даёт владелец
│   └── <тема>/                   подгруппа: muon-sign-methods, zo-estimators…
│       ├── <работа>/             ПРОЕКТ: wsd-muon, small-vocab, lora-muon…
│       └── literature/           ПРОЕКТ: разборы статей этой темы
└── …
grants/                           ОТДЕЛЬНАЯ группа верхнего уровня, не внутри brainlab
```

Почему работа — проект, а не папка:

- **членство даётся на работу**, а сейчас оно даётся на папку внутри общего репозитория,
  и держать его приходится в отдельном файле доступа сбоку;
- **доска задач у проекта**, и доска нужна именно на работу — «что делать по этой статье»;
- **заявка на доступ у проекта**: человек нажимает «хочу сюда» в той работе, куда хочет;
- **перенос работы между темами — перенос проекта между группами**, и GitLab это умеет сам.
  30-09-2026 такой перенос внутри Gitea делался руками в три шага и кончился тем, что одна
  работа полдня лежала в двух темах, с двумя открытыми предложениями на одну ветку, и агент
  называл номер из старой. На GitLab это одно действие, и история переезжает вместе с
  проектом.

Почему гранты — **отдельная группа верхнего уровня**: чтение всей лаборатории раздаётся на
группу `brainlab` и наследуется вниз. Всё, что не должно наследовать это чтение, обязано
лежать вне её, а не полагаться на исключение. Сегодня то же самое сделано списком
репозиториев в команде чтения, и список приходится досыпать руками при появлении темы.

## Литература — отдельный проект, и это следствие, а не прихоть

Разборы статей правятся **без merge request**, прямо в основной ветке: это общее знание, и
ворота там были бы помехой. Сегодня это держится настройкой Gitea «незащищённые пути»
внутри защищённой ветки.

**У GitLab такой настройки нет.** Защита ветки там не знает про пути. Поэтому литература
выносится в свой проект темы: его основная ветка не защищена, и Developer пишет в неё
напрямую, а проекты работ остаются защищёнными. Правило сохраняется, механизм меняется.

## Права

Так вышло на деле. Таблица ниже — не замысел, а то, что стоит и проверено.

| наше | GitLab | что может |
|---|---|---|
| участник лаборатории | Developer на группе `brainlab` | видит всё, пушит ветку в любую работу, заводит свои работы, не сливает нигде |
| ведущий темы | Maintainer на подгруппе темы | сливает в своей теме, и только в ней |
| вкладчик работы | Developer на проекте работы | то же, что участник |
| ведущий лаборатории | Owner на группе | всё |
| машина, агент | своя учётка `<логин>-agent`, личный ключ | состоит там же, где человек, но не выше Developer: пушит ветку, открывает предложение и ставит задачи, слить не может |

Два следствия, которых в замысле не было.

**Чтение не раздаётся вовсе.** Дерево лаборатории имеет видимость `internal`: его видит
любой, кто вошёл, а регистрация закрыта, значит «вошёл» и есть «участник лаборатории». То,
что в Gitea держалось командой чтения и расходилось с правдой при каждой новой теме,
здесь держится одним свойством группы. Записей о членстве на всю базу — четыре.

**Гость оказался не нужен.** Гость ничего не может предложить, а участнику нужно уметь
завести работу, поэтому обычный уровень — Developer. Право заводить работу даёт свойство
группы `project_creation_level = developer`; новую **тему** по-прежнему заводит Maintainer
или владелец, потому что для подгрупп GitLab других уровней не знает.

Наследование считается: владельцу корня не пишут 53 записи членства в темах, он их
владелец и так. Проход `gitlab_people.py roles` это учитывает и не плодит шум.

Проверено делом: участник пушит ветку в чужую работу и открывает предложение, а попытка
слить отвергается. В защищённую `main` не пишет даже админский ключ — только слияние.

## Доски

Доска — у проекта работы: у группы их в бесплатной версии нет, это проверено запросом, а не
прочитано (`404` на создание доски группы).

Столбцы описывают не утверждения, а **что делать**: утверждения живут в файлах и меняются
слиянием. Открытые и закрытые задачи GitLab держит своими столбцами, между ними стоят два:

```
открыто → делается → на проверке → закрыто
```

Ярлыки общие на всю лабораторию, заведены на корневой группе и наследуются всеми
проектами: `вопрос`, `прогон`, `выкладка`, `текст`, `долг` — род дела; `делается`,
`на проверке` — ход. Рода взяты из того, чем база уже различает записи, а не придуманы.

**Открытые вопросы работ стали задачами.** Они лежали списком пунктов в README, где их
нельзя ни назначить, ни обсудить по одному, ни закрыть, а проверки ругались, когда их
набиралось больше семи. Теперь каждый вопрос — задача с ярлыком `вопрос` и ссылкой на
README: 179 задач по 28 работам. README остаётся источником правды: вопрос ушёл оттуда —
задача закрывается с пояснением. Если README не прочитался, проход пропускает работу
целиком и говорит об этом: иначе пустой разбор закрыл бы все её задачи как устаревшие.

## Проверки: пока служба, а не CI

Замысел был перевести проверки в `.gitlab-ci.yml`. На деле они остались службой, которая
обходит открытые предложения раз в пять минут (`--every 300`): это
`lab-knowledge-pr-checks-gitlab.service` у пользователя `shkodnik1917` на brain_lab, код в
`~/brainlab-stack/lab-knowledge`. Причина проста: бегунок CI ещё не поставлен, а путь через
состояние коммита работает и без него. Задержку стоит помнить: вердикт появляется не сразу,
и предложение в первые минуты честно выглядит непроверенным.

Обход идёт по группам `brainlab`, `grants` и `ops` (`LAB_KNOWLEDGE_GROUPS`). До 08-10-2026
группа выводилась из пути самой службы, поэтому проверялся только `brainlab`: 59 проектов
против пяти в `grants` и `ops`, то есть предложение в грант не проверял никто.

Зато нашлось то, чего у Gitea не было вовсе. Свойство проекта
`only_allow_merge_if_pipeline_succeeds` считает и внешнее состояние коммита, то есть наш
вердикт: при красном GitLab отвергает слияние, при зелёном сливает. Проверено обеими
половинами. Включено оно не везде: на 08-10-2026 у `brainlab/handbook`, `brainlab/tools`,
`grants/grants` и научных работ да, у `brainlab/journal` и `ops/management` нет. Там, где
свойство включено, статус слияния в первые минуты читается как `ci_must_pass` — это ещё не
запрет, а ожидание вердикта.

## Что останется прежним

- **дерево знания внутри работы** — `claims/<H-код>/` с прогонами, сериями, выкладками и
  рисунками. Оно не зависит от того, чей сервер хостит git;
- **единственный путь записи** — ветка, merge request, слияние человеком;
- **чтение базы с диска** — служба продолжает читать зеркальные клоны, а не ходить по API.
  Одна правка тут всё же понадобилась, и лучше знать о ней заранее: пока тема была
  репозиторием, тему давало имя каталога. Когда работа становится проектом, зеркало — это
  репозиторий одной работы, и тему держит каталог над ним. Читающая часть научена обеим
  раскладкам: приставкой служит имя репозитория, и то же правило само собой покрывает
  проект литературы. Проверено на живой теме — обе раскладки дают одинаковые числа по
  всем видам записей, расхождений ноль;
- **прогон записывает код**, а не человек.

## Чего это стоит

Честно, до начала работ:

- **проектов станет больше**: сегодня 26 репозиториев, станет около 60 (33 работы плюс
  литература на каждую тему). Зеркал столько же;
- **словари терминов живут в вики**, а импортёр Gitea их не переносит. Переносить своим
  проходом и проверять по числу терминов, а не по коду возврата;
- **коды записей остаются сквозными внутри работы**, и это по-прежнему ярлыки, а не адреса:
  при перенумерации они меняются. Ссылаться между проектами надо путём или UUID;
- **GitLab тяжелее Gitea**. Мерить до переключения, а не после.

## Порядок, в котором это заводится

1. группа `brainlab`, подгруппы направлений, подгруппы тем;
2. отдельная группа `grants`;
3. импорт репозиториев тем как временных проектов;
4. разделение каждой темы на проекты работ и проект литературы — обычным
   `git subtree split -P <работа>`, история работы при этом сохраняется. Проверено на
   теме из двух работ: 77 коммитов темы дали 35 и 3 у работ;
5. защита веток в проектах работ, литература без защиты;
6. чтение на группу, членство на проекты;
7. доски и метки;
8. `.gitlab-ci.yml` с проверками;
9. зеркальные клоны и переключение корня чтения;
10. заявки на доступ включаются сразу, это то, чего не хватало.

Шаги 1–2 требуют названий направлений: их даёт владелец, и без них раскладка остаётся
плоской, какой она сегодня и есть.

## Чем это поддерживается

Каждая настройка собирается проходом, а не руками, и каждый проход повторно безопасен.
Лежат в `services/lab-knowledge/scripts/`.

| проход | что делает |
|---|---|
| `gitlab_tree.py` | дерево групп: направление, тема, гранты отдельно |
| `gitlab_move.py` | перенос темы из Gitea, история работы расколом `subtree split` |
| `gitlab_delta.py` | чего в GitLab ещё нет, а в Gitea уже есть; литературу досылает сам |
| `gitlab_guard.py` | ворота: в `main` только слиянием, литература без ворот нарочно |
| `gitlab_people.py` | учётки, роли из базы, право заводить работу |
| `gitlab_keys.py` | учётка агента человека и личный ключ на машину, срок год |
| `gitlab_requests.py` | заявки на доступ: показать, одобрить, отказать |
| `gitlab_visibility.py` | видимость из шапки README работы |
| `gitlab_cards.py` | имя, описание и метки проекта из его README |
| `gitlab_board.py` | ярлыки лаборатории, доски работ и групп, оснастка работы |
| `gitlab_profile.py` | передняя страница группы: предмет области и список работ |
| `gitlab_api.py` | один клиент на все проходы: страницы, отказы, годные имена |

Предмет области темы при переезде остался без места: тема перестала быть репозиторием, и её
README никто не показывал. Закрыто родной возможностью GitLab — проект `gitlab-profile`
внутри группы становится её передней страницей. Текст взят из старого README темы, список
работ пересобирается каждым проходом и потому не устаревает. Зеркало базы такой проект не
читает: иначе в базе появилась бы работа-призрак.
