# Переезд с Gitea на GitLab

Решение принято 30-09-2026. Причина не «GitLab лучше», а три вещи, которых у Gitea нет и не
появится. Всё остальное — репозитории, ветки, pull request, права, защита ветки, галочки
проверок — у обоих есть, и ради этого переезжать было бы незачем.

## Зачем

**1. Дерево групп.** Нужно направление → тема → работа. У Gitea одна плоская организация:
в описании её собственного API 308 путей, 34 из них про организации, и ни одного про
вложенность или подгруппы; у объекта организации нет поля «родитель». В GitLab группы
вложены изначально.

**2. Доска задач, доступная агенту.** В описании API Gitea **ноль** путей про доски. Доски
есть в интерфейсе, но агент их не тронет, а канбан нужен именно агентам. Костыль на метках
владелец отверг прямо: «делать костыльный через гитею канбан мы не будем».

**3. Заявка на доступ.** Нужно, чтобы человек сам нажал «хочу в этот проект», а ведущий его
принял. В бинарнике Gitea 1.27.3 нет ни одной такой строки; два вхождения `request_access`
там есть, но это `json:"request_access_enabled"` в её клиенте **GitLab API**, то есть в
импортёре чужой системы. Оттуда же и следует, что в GitLab это штатное поле проекта и
группы.

## Что измерено

```
клиент gitea.py            380 строк, 10 вызовов API
зовут его                  3 файла, около 30 мест, через один объект
база читает репозитории    прямо с диска, по имени каталога
```

Десять вызовов, которые надо повторить:

| Gitea | зачем | GitLab |
|---|---|---|
| `POST contents` | записать файлы одним коммитом | `POST repository/commits` |
| `GET pulls` | открытые предложения | `GET merge_requests` |
| `POST pulls` | открыть предложение | `POST merge_requests` |
| `GET pulls/{n}` | прочитать одно | `GET merge_requests/{iid}` |
| `PATCH pulls/{n}` | переписать тело | `PUT merge_requests/{iid}` |
| `POST pulls/{n}/update` | подтянуть основную ветку | `PUT merge_requests/{iid}/rebase` |
| `POST issues/{n}/comments` | комментарий | `POST merge_requests/{iid}/notes` |
| `POST statuses/{sha}` | поставить галочку | `POST statuses/{sha}` |
| `GET commits/{sha}/statuses` | прочитать галочки | `GET commits/{sha}/statuses` |
| `DELETE branches/{имя}` | убрать ветку | `DELETE repository/branches/{имя}` |

Соответствие один в один, меняются адреса и имя идентификатора: у GitLab это `iid` внутри
проекта, а не номер внутри репозитория.

## Узкое место

**База читает голые репозитории с диска, по имени каталога.** Так она грузит 33 работы, 646
разборов литературы и словари за секунды — одним `git cat-file --batch` на репозиторий.

У GitLab так нельзя: хранилище хешированное (`@hashed/xx/yy/<sha256 от id проекта>.git`), по
имени не найти, а прямой доступ к каталогу объявлен устаревшим — полагается ходить через
Gitaly.

**Решение — зеркальные клоны.** На каждую тему `git clone --mirror`, рядом служба
периодического `fetch`. Тогда читающая часть не меняется вовсе: меняется только корень в
`LAB_KNOWLEDGE_GIT_ROOT`. Ходить по API вместо диска нельзя — это сотни запросов на одну
загрузку вместо одного процесса.

Как база ляжет на GitLab — какая группа чем становится, где доски, где права и
почему литература выносится в свой проект: [gitlab-layout.md](gitlab-layout.md).

## Порядок работ

**Шаг 0. Развернуть GitLab рядом, ничего не выключая.** Gitea продолжает работать, служба
продолжает читать её. Пока не сделано: нет прав на docker на сервере лаборатории, нужен
владелец.

**Шаг 1. Завести дерево групп.** Направление — группа, тема — подгруппа, работа — проект.
Это то, ради чего переезд: сейчас все 33 работы лежат плоско, и поле направления у них
пустое. Названия направлений даёт владелец; сопоставление тем берётся из нынешних
репозиториев.

**Шаг 2. Перенести содержимое.** У GitLab есть импортёр Gitea: репозитории, задачи,
merge request, вехи, метки, замечания к диффу. **Вики он не переносит** — словари терминов
живут в вики тем, их придётся перенести отдельным проходом.

**Шаг 3. Поставить зеркальные клоны и переключить корень.** Читающая часть не меняется.
Проверка: число работ, утверждений, прогонов и статей до и после совпадает.

**Шаг 4. Переписать клиент.** Один файл, десять вызовов, таблица выше. Проверка: открыть
предложение, дописать в него, поставить галочку, прочитать её, удалить ветку — на
одноразовом проекте.

**Шаг 5. Перенести ворота.** Защита основной ветки, список тех, кто может сливать, список
незащищённых путей для литературы. У GitLab это `protected_branches` и `push_rules`.

**Шаг 6. Перевести участников.** Учётные записи, ключи, членство. Заявку на доступ
включить сразу: это то, чего не хватало.

**Шаг 7. Выключить Gitea, оставив её данные.** Голые репозитории — полный слепок базы, и
терять их незачем.

## Чего переезд не чинит

- **состав участников** — его всё равно заполнять людям, просто удобнее;
- **предложения в памяти службы** — это не про хранилище, а про то, что их надо хранить
  в git или в базе;
- **долг работ** — замечания проверок никуда не исчезнут от смены сервера.

## Что появится после

- дерево направление → тема → работа вместо плоского списка;
- канбан, доступный агенту по API: задача, исполнитель, столбец, срок;
- заявки на вступление в проект: человек нажимает, ведущий принимает;
- нормальные участники проектов и группы вместо ручной раздачи.

## Риски, названные заранее

- **Вики не переносится импортёром.** Словари терминов — 186 записей — переносить своим
  проходом. Проверять по числу терминов, а не по коду возврата.
- **Хешированное хранилище.** Если зеркала окажутся дороже, чем кажется, читающая часть
  всё равно остаётся рабочей: она читает зеркала, а не GitLab.
- **GitLab тяжелее.** Gitea работает службой пользователя без root; GitLab требует
  заметно больше памяти. Замерить до переключения, а не после.
- **Двойной период.** Пока живы оба, работа может оказаться в двух местах. 30-09-2026 это
  уже случилось при переносе одной работы между темами внутри Gitea: два открытых
  предложения на одну ветку в разных репозиториях, и агент называл номер из старого. Вывод
  на будущее: переносить работу целиком одним проходом и закрывать старое предложение в
  том же проходе.
