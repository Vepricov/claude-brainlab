# База знания лаборатории: как в неё писать

**Это обычный git-репозиторий, склонированный тебе на машину.** Работай с ним как с любым
другим: ветка, правка файлов, коммит, предложение. Ничего поверх git учить не надо.

Две вещи, которых у обычного репозитория нет. Первая: **push в `main` запрещён всем**,
включая администратора, поэтому правка входит только слиянием предложения — и слияние
человеком и есть запись в базу. Вторая: **в одном репозитории живёт одна работа**, а
знание в нём лежит папками `claims/<КОД>/`.

## Клон у себя, а не ходить на сайт

```bash
lab here <работа>     # клон ляжет рядом с кодом, в lab-base; путь искать не надо
lab pull              # что изменилось в main и что уже открыто
```

Дальше обычный git: ветка, правка файлов, коммит. На сайт ходить незачем — задачи,
предложения и вердикты видны из терминала. У `lab` осталось ровно то, чего git не умеет:
найти работу по слагу, положить ключ туда, где git его найдёт, и прочитать задачи с
вердиктом — `lab here`, `lab pull`, `lab tasks`, `lab take`, `lab checks`. Всё остальное
делается git'ом, и обёрток под это нет нарочно.

## Что лежит в работе

Обязательна одна папка — `claims/`. Остальное по надобности, и больше ничего:

```
<работа>/
├── README.md              о чём работа, где её код и статья, список утверждений
├── claims/H-XXX-001/      УТВЕРЖДЕНИЕ — это папка
│   ├── README.md          что утверждаем и чем это опровергается
│   ├── runs/E-….md        прогон: настройки, числа, где их проверить
│   ├── series/S-….md      серия: один вопрос, ось сравнения, вердикт
│   ├── theory/D-….md      выкладка с доказательством
│   └── figures/F-….svg
├── code/                  обучающий код или ссылка на него
├── paper/                 вёрстка статьи; обычно git-клон Overleaf, в `.gitignore`
├── calls/<дата>.md        записи созвонов: заметки, не знание
├── notes/                 черновое и рабочее: ничего не обязано быть готовым
└── .gitlab/issue_templates/
```

Работа лежит в дереве один раз, но может **показываться в нескольких темах**. Для этого в
шапке README поле `topics`: слаги через запятую. Слаг, совпавший с темой или направлением
дерева, означает «показывать работу и там» — она появится в списке проектов той группы
целиком, той же работой, а не копией и не ссылкой. Уровень там читательский: дома у работы
одна тема, и писать в неё — дело её команды.

Папка, которой нет в этом списке, объясняется в README одной строкой; иначе её не
заводить. Почему так строго — ниже, «Главное правило».

## Порядок записи

**Прогон пишет код, а не человек.** Гиперпараметры, числа, коммит и железо знает только
то, что считало. В репозиторий с обучением кладётся `lab_run.py` из работы `tools`, и
прогон ложится файлом сам: настройки, метрики, версия torch, карта, номер задачи. Падение
не теряется — OOM закрывает запись статусом `failed` с причиной. Это самый надёжный
кирпичик, и начинать надо с него.

**И уезжает в базу сам, в твою же ветку.** Ту, в которой ты потом напишешь предложение:

```bash
export LAB_RUN_BRANCH=claim/H-WSD-009    # ветка, в которой будешь писать
python train.py ...                       # прогон уедет туда же
```

Не сказал — уедет в `runs/<машина>`. Уезжает не json, а **папка прогона** `_runs/<имя>/`:
`README.md` со страницей (зачем, итоговые числа, где проверить, настройки, чем считали),
`metrics.csv` с полным логом и всё, что приложили через `run.attach(...)` — графики,
конфиги, выдержки логов. Пустыми нарочно оставлены `code` и `claim`: свободный код берёшь из
клона, утверждение выбираешь ты.

Твоя работа: перенести папку в `claims/<H-код>/runs/<E-код>.md` (и файлы рядом) и дописать
прозу. Числа не переписывай, они уже там.

**Скажи, зачем прогон:** `LabRun(objective="…")`, пара предложений себе будущему. Это
единственное, чего нет в числах.

Полка проверяется, а не напоминается: `git status` её показывает, и **предложение не
сольётся, пока `_runs/` не пуста** — проверка даёт красный вердикт и перечисляет, что
осталось.

Серию, утверждение и выкладку пишет агент. Свободный код берётся **из клона**: по каждой
букве (`H`, `E`, `S`, `D`, `F`) смотрится наибольший номер, а не количество файлов — дыры в
нумерации настоящие, и счётчик даёт занятый код.

```bash
cd lab-base
ls claims                              # коды утверждений этой работы, как есть
git checkout -b claim/<H-код>          # одно предложение на утверждение
$EDITOR claims/<H-код>/runs/<E-код>.md
git fetch --all --prune && git merge --no-edit main   # merge, НЕ rebase
git diff --stat main..HEAD             # посмотреть ГЛАЗАМИ
git commit -F -                        # заголовок и тело предложения прямо в коммите
git push -o merge_request.create \
         -o merge_request.assign=veprikov   # предложение откроется и встанет к тому, кто сливает
lab checks                             # что сказали проверки
```

**Тело предложения берётся из сообщения коммита**: первая строка — заголовок, остальное —
тело. `Closes #7` там же, своей строкой: слияние закроет задачу само.

**Исполнителем ставь того, кто будет сливать.** GitLab по умолчанию назначает предложение его
автору, а автор — учётная запись агента; у человека тогда в «Merge requests → Assigned» ноль,
и он твоего предложения не видит. Забудешь — часовой проход поставит ведущего проекта сам, но
лучше сразу.

Ветка от устаревшего `main` показывает в предложении удаление чужих файлов, и проверка
этого не ловит. Поэтому `merge` и взгляд на diff обязательны. `rebase` ломает push и тянет
к `--force-with-lease`, которым ветку однажды уже снесли.

**В теле предложения три вещи, и ни одну нельзя пропустить:** что изменилось и зачем; что
исчезло и почему; чем проверено. Третья существует потому, что однажды при зелёном вердикте
молча ушли семь измеренных чисел.

## Задачи

```bash
lab tasks                  # что открыто, кому назначено, какое утверждение затрагивает
lab take 7                 # взять на себя: исполнитель и ярлык «делается»
```

Закрыть задачу — строкой `Closes #7` в сообщении коммита: слияние закроет её само.

У задачи в теле строка **«Утверждение: H-XXX-NNN»** — то, на что она влияет. Открытые
вопросы работы задачами не заводятся: они живут на страницах своих утверждений.

Новую задачу агент заводит сам, обычным вызовом (`POST projects/<путь>/issues`), и там же
ставит исполнителя. Отдельного права на это нет: кто может открыть предложение, тот может и
поставить задачу — у агента своя учётная запись, и состоит она там же, где человек. Задачи
не про науку живут не в работе, а в группе `ops`. Исполнителем встаёт только тот, кто в
проекте состоит: иначе GitLab отвечает 200 и молча ничего не делает, и тогда имя того, кому
поручено, пишется первой строкой в теле.

## Главное правило: не мусорить

Остальные ограничения мягкие, это — нет. Мусор в общей базе дороже пустоты: пустое место
видно, а мусор читают как знание.

- **Выдуманных чисел нет.** Ни одного, которого нет ни в корпусе, ни в приложенном логе.
- **Записи без утверждения не бывает.** Лог и таблица — опора под утверждением; нет
  утверждения, под которое это идёт, — либо сформулируй его, либо не пиши.
- **Новых папок, разделов и полей не заводить.** Нет такого у эталонной работы `dykaf` —
  спроси, а не придумывай.
- **Мусорный мешок запрещён под любым именем** (`archive/`, `old/`, `tmp/`). Утверждение,
  которое больше не нужно, отдаёт свой корпус живому и уходит целиком. Владелец
  26-09-2026: «никакого мусорного мешка быть не должно».
- **Чекпоинт, локальная заметка и незелёное предложение записью не являются.** Адрес
  записи — путь файла в репозитории. Отложенное назвать вслух, а не оставить в переписке.
- **Запись через MCP записью не считается.** Служба на неё отвечает отказом; путь один —
  предложение.
- **Чужие замечания не чинить в своём предложении.** Проверка судит правку, а не работу
  целиком, и старый долг работы тебе не мешает.
