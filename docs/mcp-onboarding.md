# База знания BRAIn Lab: инструкция участника

Читается за десять минут. Всё проверено 30-09-2026 на живой базе.
## Что это

Общая память лаборатории. **Это git.** Репозиторий на каждое научное направление, внутри — работы, их утверждения, прогоны, числа и разборы статей. Никакого отдельного приложения: ты клонируешь репозиторий, правишь файлы, делаешь pull request. Всё остальное — проверки, поиск, веб — надстройки над этим.

Зачем: чтобы на вопрос «а это кто-нибудь уже пробовал» был ответ, и чтобы у числа в статье был адрес, по которому его можно открыть и проверить. Приватное и незрелое остаётся в личных заметках. Сюда попадает проверяемое.

Сейчас внутри: 26 репозиториев, 33 работы, 149 утверждений, 319 серий, 923 прогона, 790 измерений, 646 разобранных статей.

## Шаг 1. Получить доступ

[@brainlab_server_access_bot](https://t.me/brainlab_server_access_bot) — тот же бот, что выдаёт доступ к серверам, только в личном чате.

1. **«Мой профиль»** — имя, фамилия, кто рекомендует. Без профиля заявка не уйдёт.
2. **«Получить доступ»** → в списке «Серверы и база знаний» выбрать **«База знаний MCP»** → роль → **«Подать заявку»**.
3. Андрей смотрит заявку, и бот присылает всё сразу:

| что | зачем |
|---|---|
| адрес базы | нужен и агенту, и git |
| ключ MCP | чтение и поиск по базе из агента |
| идентификатор `telegram-123…@users.brainlab-ai.com` | твоё имя внутри базы, им тебя добавляют в работу |
| логин на сайте и временный пароль | вход в браузере |
| ключ для git | им твоя машина ходит в репозитории |

Сохрани идентификатор: именно его называют, когда дают доступ к работе.

## Шаг 2. Войти на сайт и сменить пароль

**Это обязательно и именно сейчас.** Пока пароль временный, Gitea не пускает и git тоже: `git clone` отвечает `remote: Update your password`, и выглядит это как сломанный ключ.

Откроешь сайт по адресу из сообщения бота, войдёшь логином и временным паролем, сменишь пароль — и всё остальное заработает.

Заодно посмотри, как всё выглядит: сайт это и есть база. В нём видны темы, работы, pull request, и слияние pull request в браузере есть запись в базу.

## Шаг 3. Склонировать базу

Клон живёт **на твоей машине** — на ноутбуке, на сервере, где считаешь, или и там и там. Это обычный локальный репозиторий, ничего общего ни с кем.

```bash
curl -fsSL https://raw.githubusercontent.com/brain-lab-research/claude-brainlab/main/scripts/lab \
  -o ~/.local/bin/lab && chmod +x ~/.local/bin/lab

# три строки из сообщения бота, достаточно один раз — они запомнятся
export LAB_GIT_URL=АДРЕС_БАЗЫ
export LAB_GIT_LOGIN=ТВОЙ_ЛОГИН
export LAB_GIT_TOKEN=КЛЮЧ_ДЛЯ_GIT

lab clone
```

Ложится в `~/brainlab-stack/git-base/<тема>/`. Адрес, логин и ключ сохраняются в `~/.config/brainlab/` с правами `600`, и ключ попадает в один файл, а не в настройки каждого клона.

Работаешь на нескольких машинах — повтори эти четыре строки на каждой.

**Ключи ssh настраивать не надо.** В Gitea ssh выключен нарочно: люди читают в браузере, машины ходят по HTTPS с токеном.

## Шаг 4. Посмотреть, как всё разложено

```
<тема>/                          репозиторий: muon-sign-methods, zo-estimators…
├── README.md                    предмет направления и список работ
├── literature/<ключ>.md         разборы статей, общие для всей лаборатории
└── <работа>/                    wsd-muon, small-vocab, lora-muon…
    ├── README.md                чем работа занята
    └── claims/H-XXX-001/        утверждение — это папка
        ├── README.md            что утверждаем и чем это опровергается
        ├── runs/E-XXX-001.md    прогон: настройки, числа, где их проверить
        ├── series/S-XXX-001.md  серия: что проверяли этой группой прогонов и что вышло
        ├── theory/D-XXX-001.md  выкладка с доказательством
        └── figures/F-XXX-001.svg
```

Коды — ярлыки, а не адреса: `H-` утверждение, `E-` прогон, `S-` серия, `D-` выкладка, `F-` рисунок, `R-` измерение. При перенумерации работы они меняются, поэтому в разговоре надёжнее называть путь к файлу.

**Всё стоит на утверждении.** Прогон сам по себе не знание: он опора под утверждением, которое проверяет. Новый прогон на новом масштабе почти никогда не новое утверждение — это ещё одна опора под уже существующим.

Лучший способ понять форму — открыть соседнюю работу и почитать чужие страницы. Формат страницы никем не предписан: смотри, как сделано рядом, и делай похоже.

## Шаг 5. Внести своё

Обычный git, ничего особенного:

```bash
cd ~/brainlab-stack/git-base/muon-sign-methods
lab pull                                  # что изменилось и что уже открыто
git checkout -b claim/H-WSD-001           # ветка на утверждение, которое дополняешь
$EDITOR wsd-muon/claims/H-WSD-001/runs/E-WSD-042.md
git add -A && git commit -m "E-WSD-042: прогон на 355M, три сида"
lab pr                                    # запушит и откроет pull request
lab checks                                # что сказали проверки
```

Правила ветки одно: **один pull request на утверждение**, ветка `claim/<H-код>`. Если по этому утверждению pull request уже открыт, `lab pr` скажет об этом, и твой push просто войдёт в него. Так человек читает одно дело целиком, а не двадцать несвязанных правок.

**Слить может только человек.** Слияние и есть запись в базу: служба сверяется с git перед каждым обращением и видит изменение сразу. Твой ключ сливать не может, и это единственные настоящие ворота.

## Что проверяется само

На каждый push встаёт галочка и приходит разбор в обсуждение pull request. `lab checks` показывает то же самое в терминале. Проверок три, и они одни на любую правку:

- **дерево** — прогон лежит в серии, у серии есть вердикт, у утверждения есть чем его опровергнуть, коды не повторяются;
- **числа** — каждое число на странице утверждения и серии встречается в прогонах под ними. Вывод пересказывает опору, а не добавляет к ней цифры;
- **удаления** — исчезнувшая запись названа в теле pull request.

Проверка судит **правку, а не работу целиком**: старый долг работы не мешает записать новый прогон. Замечанием становится только то, чего не было в `main`.

Самое частое замечание: **прогон не входит ни в одну серию** — тогда он не попадёт на страницу утверждения. Поставь в шапку прогона `series: S-XXX-001` и заведи страницу серии.

## Прогон пишет код, а не человек

Гиперпараметры, числа, коммит и железо знает только код, который считал. Он их и записывает. В репозиторий с обучением кладётся один файл `lab_run.py` — он лежит в базе, в `lab-agents/tools/`, только стандартная библиотека, python 3.9+:

```python
from lab_run import LabRun

with LabRun(work="small-vocab", name="vocab8k-seed0", settings=vars(args)) as run:
    for step, batch in enumerate(loader):
        run.metric("train/loss", train_step(batch), step=step)
    run.metric("val/ppl", ppl, step=step, final=True)
    run.where("brain_lab:~/runs/vocab8k-seed0/train.log")
```

Ложится `lab-runs/<имя>.json` с настройками, метриками, версией torch, картой, номером slurm-задачи и коммитом. Падение не теряется: OOM закрывает запись статусом `failed` с причиной.

**У числа обязательно место, где его можно открыть глазами**: страница в W&B, путь к логу, файл прогона. Число, которое нечем проверить, знанием лаборатории не является.

## Литература

Разборы статей в `literature/` правятся **без pull request**, прямо в `main`. Ограничение не на доверии, а в самом git: за пределы `literature/` такая правка не проходит. Проверяются ключ цитирования, разметка, наличие разделов разбора и отсутствие личных путей в ссылках.

## Что видно и кто что может

Сейчас **все работы лаборатории открыты на чтение**: любой участник видит любую работу, её утверждения, прогоны и числа. Закрыта одна работа по грантам. Литература общая изначально.

Право читать не есть право писать. Чтобы предложить правку **в чужую работу**, нужно членство в ней: `viewer` читает, `contributor` предлагает, `lead` одобряет. Членство выдаёт ведущий работы или Андрей, назвав твой идентификатор из сообщения бота.

**Свою работу можно завести самому.** Скажи агенту `create_project` с названием и темой — папка появится в репозитории темы, и ты станешь её ведущим.

Кнопки «хочу присоединиться» на сайте у Gitea нет — проверено, в ней такого механизма не существует. Поэтому пока так: посмотрел, нашёл своё, написал Андрею в личку, какие работы нужны.

## Агент и MCP

У базы есть MCP — он нужен **для чтения и поиска**: спросить словами «что у нас известно про прогрев», найти статью, посмотреть чужую работу. Писать через него не надо: агент правит файлы в клоне и делает pull request, как человек.

Подключение для Claude Code (по умолчанию сервер живёт только в этом каталоге, в остальных агент про базу не знает; `--scope user` делает его доступным везде):

```bash
claude mcp add --transport http lab-knowledge "$LAB_MCP_URL" \
  --header "Authorization: Bearer $LAB_MCP_TOKEN"
```

Для Codex ключ передаётся именем переменной, поэтому она должна быть видна процессу при каждом запуске — допиши её в `~/.zshrc`:

```bash
codex mcp add lab-knowledge --url "$LAB_MCP_URL" --bearer-token-env-var LAB_MCP_TOKEN
```

Положи рядом с кодом файл `.lab-work` с одной строкой — слагом твоей работы. Тогда агент не выясняет каждый раз, где он.

## Если не работает

- **`не знаю адреса базы`** — скажи `export LAB_GIT_URL=…` один раз, адрес в сообщении бота.
- **`remote: Update your password`** — пароль на сайте ещё временный. Зайди в браузер и смени его, после этого git заработает.
- **`repository not found`** на тему, которая точно есть — тебя ещё не добавили в организацию на сайте. Напиши Андрею.
- **git просит пароль** — не сказаны `LAB_GIT_LOGIN` или `LAB_GIT_TOKEN`. Скажи их один раз, они запомнятся.
- **`есть свои правки, не трогаю`** — ты не на `main` или есть незакоммиченное. Это не ошибка, а отказ затирать твоё.
- **`ты на main`** при `lab pr` — сделай ветку.
- **401 у MCP** — ключ неверен или отозван. Показать заново: `/mcp` у бота.
- **Сайт уводит на форму входа** — так и должно быть, он закрыт для незалогиненных. Логин и пароль в сообщении бота; сессия могла истечь.
- **`project not found`** на работу, которая точно есть — тебя в неё не позвали. Формулировка нарочно та же, что для несуществующей: иначе по разнице ответов перебирается состав базы.

## Куда писать

Андрею, включая мелочи: непонятный отказ, странную выдачу, неработающую ссылку, правило, которое мешает делать работу. База собиралась под то, как работает лаборатория, а не наоборот. Если правило мешает — это, скорее всего, ошибка правила, и вопрос «почему нельзя вот так» ценнее обхода.
