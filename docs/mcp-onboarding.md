# Подключиться к базе знаний BRAIn Lab

Общая память лаборатории. Не сайт с формами и не таблица: **это git**. Репозиторий на каждое направление, внутри — работы, их утверждения, прогоны, числа и разборы статей. MCP, проверки и веб — надстройки над ним.

Всё ниже проверено 30-09-2026 на живой базе. Адреса приходят в сообщении бота: репозиторий с этим файлом открытый, а база — нет.

## Получить доступ

1. Открыть [бота доступа](https://t.me/brainlab_server_access_bot) в личном чате — тот же, что выдаёт доступ к серверам.
2. Нажать **«Мой профиль»**, указать имя, фамилию и рекомендателя. Без профиля заявка не уйдёт.
3. Нажать **«Получить доступ»**, в списке «Серверы и база знаний» выбрать **«База знаний MCP»**, под ней роль, затем **«Подать заявку»**. Срок доступа для одного MCP указывать не нужно.
4. Андрей смотрит заявку и выбирает роль. Бот присылает адрес базы, личный ключ и идентификатор вида `telegram-123456789@users.brainlab-ai.com` — это ваше имя внутри базы, им вас добавляют в работу. Сохраните его.

Учётная запись привязана к постоянному Telegram ID, а не к нику. Показать ключ заново или отозвать: команда `/mcp` у бота. SSH-доступ к вычислительным серверам для базы не нужен.

## Подключить агента

### Только в одной папке, а не везде

Это поведение **по умолчанию**. У `claude mcp add` есть `--scope`, и он по умолчанию `local`: сервер записывается только для текущего каталога, в остальных агент про базу не знает и подключаться к ней не будет.

| scope | где действует | где хранится |
|---|---|---|
| `local` (по умолчанию) | только этот каталог, только у вас | ваш личный конфиг, привязанный к пути |
| `project` | этот каталог у всех, кто его склонирует | `.mcp.json` рядом с кодом |
| `user` | все каталоги | ваш личный конфиг |

То есть «пусть пишет только по одному проекту» делается так: зайти в каталог этого проекта и добавить сервер **без** `--scope user`.

```bash
cd ~/Papers/мой-проект
export LAB_MCP_URL='АДРЕС_ИЗ_СООБЩЕНИЯ_БОТА'
read -r -s -p 'Личный ключ: ' LAB_MCP_TOKEN && export LAB_MCP_TOKEN
claude mcp add --transport http lab-knowledge "$LAB_MCP_URL" \
  --header "Authorization: Bearer $LAB_MCP_TOKEN"
```

Если нужно наоборот, во всех каталогах — добавить `--scope user`.

Проверить: перезапустить Claude Code и набрать `/mcp`. В списке должен быть `lab-knowledge` с признаком подключения.

### Codex CLI

Ключ передаётся **именем переменной**, а не значением, поэтому переменная должна быть видна процессу Codex при каждом запуске: допишите её в `~/.zshrc` или `~/.bashrc`.

```bash
codex mcp add lab-knowledge --url "$LAB_MCP_URL" --bearer-token-env-var LAB_MCP_TOKEN
codex mcp list
```

### Клиент с ручной настройкой

Транспорт **HTTP / Streamable HTTP**, имя подключения `lab-knowledge`, заголовок `Authorization: Bearer ВАШ_КЛЮЧ`.

### Привязать папку к работе

Чтобы агент не выяснял каждый раз, в какой работе он находится, положите рядом с кодом файл `.lab-work` с одной строкой — слагом работы:

```bash
echo small-vocab > .lab-work
```

Это дешевле любого поиска: агент читает файл, а не тратит вызовы на «где я».

## Ключи: чей и что может

Право живёт **в ключе**, а не в учётной записи. Это сделано нарочно: иначе агент с личным ключом человека проходит ворота как человек.

| | человек | его агент |
|---|---|---|
| читать базу | да | да |
| предложить запись (`propose`) | да | **да, это единственный путь** |
| написать запись напрямую | **нет** | нет |
| одобрить и слить | да, слиянием в браузере | никогда |
| завести работу | да | да |
| позвать человека в работу | да, если ведущий её | нет |

Ключ, который выдаёт бот, — агентский: он не может ни записать напрямую, ни одобрить. Завести свою работу может: работа — это пустая папка, а знание попадает в неё только слиянием. Это и есть ворота.

**Напрямую в базу не пишет никто, включая ведущего лаборатории.** Знание живёт в git, и запись, не прошедшая через слияние, до него не доходит: раньше такая запись принималась и исчезала при следующем чужом слиянии, теперь служба на неё отказывает и называет путь. Одно правило для всех.

Ключ не кладётся в репозиторий, не пересылается в общий чат и не печатается в логах. Свой ключ для каждой машины и каждого агента: общий ключ на трёх агентов делает журнал бесполезным — не видно, кто писал.

**Агент на сервере** (например, Гермес на do-vpn) получает свой ключ с меткой машины через `issue_agent_token`, а не переиспользует чужой. Ключ лежит файлом с правами `600`, а не в переменной в истории оболочки. Отозвать можно отдельно от учётной записи.

## Как запись попадает в базу

```
агент → propose → ветка → pull request → проверки → человек сливает
```

Слияние и есть запись: служба сверяется с git перед каждым обращением и видит изменение сразу, без перезапуска.

Один pull request на утверждение. Следующее предложение по тому же утверждению доливает коммит в тот же PR, а не заводит второй: читается одно дело целиком.

Предложение несёт не одну запись, а **мысль вместе с опорой**: что утверждается, чем подтверждается, и что из этого следует записать. Без проверяемой опоры — числа, кода прогона, теоремы, места в рукописи — предложение отклоняется сразу. Новое утверждение вдобавок обязано назвать **механизм** (почему это верно) и **условия** (модели, масштабы, режим): утверждение, верное ровно там, где его померили, — это личная заметка, а не знание лаборатории.

## Что проверяется само

На каждый pull request встаёт галочка, и проверки одни на любую правку — писать их к своему коммиту не надо:

- **дерево** — прогон лежит в серии, у серии есть вердикт, у утверждения есть чем его опровергнуть, коды не повторяются;
- **числа** — каждое число на странице утверждения и серии встречается в прогонах под ними;
- **удаления** — исчезнувшая запись названа в теле pull request.

Проверка судит **правку, а не работу целиком**: старый долг работы не мешает записать новый прогон.

## Прогон пишет код, а не агент

Гиперпараметры, числа, коммит и железо знает только код, который считал. В репозиторий с обучением кладётся `lab_run.py` (лежит в `brainlab/lab-agents/tools/`, только стандартная библиотека, python 3.9+):

```python
from lab_run import LabRun

with LabRun(work="small-vocab", name="vocab8k-seed0", settings=vars(args)) as run:
    for step, batch in enumerate(loader):
        run.metric("train/loss", train_step(batch), step=step)
    run.metric("val/ppl", ppl, step=step, final=True)
    run.where("brain_lab:~/runs/vocab8k-seed0/train.log")
```

Ложится `lab-runs/<имя>.json` с настройками, метриками, версией torch, картой, номером slurm-задачи и коммитом. Агент отправляет файл вызовом `submit_run`, назвав только утверждение и серию. Ни числа, ни настройки снаружи задать нельзя: число, прошедшее через языковую модель, проверить уже невозможно.

## Записывает агент, и записывает сам

Отдельной разметки, полей и обрядов нет. Агент решает сам, когда записать, и пишет одним вызовом `propose`: предложение открывает pull request, человек его сливает. Формы у предложения нет — пусть пишет так, как понятнее, лишь бы без мусора и с опорой.

Чтобы он не тратил токены на «где я» и не путался в номерах, ему при старте сессии кладут в контекст три вещи, и все три с диска или одним запросом, без вызовов модели:

- в какой работе он находится (файл `.lab-work` рядом с кодом или карта путей);
- какие в этой работе утверждения;
- **какие pull request уже открыты** — чтобы он дописывал в существующий, а не заводил второй.

Последнее важнее, чем кажется. 30-09-2026 агент доложил про pull request №2, давно закрытый, вместо открытого №3: он взял номер из своей прошлой памяти. Поэтому блок про открытые предложения теперь идёт **первым** в ответе про работу, а не в его конце — ответ по большой работе весит под двести килобайт, и хвост до читателя не доходит.

Ставится это одной строкой:

```bash
bash install/setup.sh
```

Прежний хук разметки (`ЛАБ-ГИПОТЕЗА:`, `ЛАБ-ЧИСЛО:` и прочие) выключен. Он был из того времени, когда запись шла напрямую, и заставлял человека заполнять поля вместо того, чтобы агент написал сам.

## Что видно и как попасть в работу

Сейчас **все работы лаборатории открыты на чтение**: любой участник видит любую работу, её утверждения, прогоны и числа. Закрыта работа по грантам — её видят причастные. Литература общая изначально.

Право читать не есть право писать. Чтобы что-то **предложить** в работу, нужно членство в ней: `viewer` читает, `contributor` предлагает, `lead` одобряет. Членство выдаёт ведущий работы или Андрей, назвав ваш идентификатор из сообщения бота.

Пока что так: посмотрели, нашли своё, написали Андрею в личку, какие работы вам нужны. Кнопки «хочу присоединиться» на сайте у Gitea нет — проверено, в ней такого механизма не существует.

Свою работу можно завести самому: `create_project` с названием и темой. Знание в неё всё равно попадает только через `propose` и слияние.

## Если не работает

- **401** — ключ неверен, отозван или учётная запись отключена. Показать заново: `/mcp` у бота.
- **`project not found`** на работу, которая точно есть — вас в неё не позвали. Формулировка нарочно та же, что для несуществующей работы: иначе по разнице ответов перебирается состав базы.
- **`an agent does not write to the base directly`** — всё правильно, запись идёт через `propose`.
- **`this base keeps its knowledge in git, and a direct write does not reach it`** — запись пошла мимо `propose`. Так отвечает и ведущему.
- **`call N: mechanism is too short`** или **`a new claim needs its case`** — новое утверждение без механизма, условий или без опоры под ним. Это не поломка, а требование к утверждению.
- **`carries a number but says nowhere to check it`** — у числа нет адреса. Передайте `where_to_check`.
- **Первый поиск после простоя идёт секунд десять** — это нормально, дальше быстрее. Случайный `502` — повторить.

## Куда писать

Андрею, включая мелочи: непонятный отказ, странную выдачу, неработающую ссылку, правило, которое мешает делать работу. База собиралась под то, как работает лаборатория, а не наоборот. Если правило мешает, это, скорее всего, ошибка правила, и вопрос «почему нельзя вот так» ценнее обхода.
