# База знания BRAIn Lab: инструкция участника

Читается за десять минут. Всё, что ниже, проверено 01-10-2026 на живой базе.

## Что это

Общая память лаборатории. **Это git.** У каждой работы свой репозиторий, работы сложены по темам, темы — по направлениям. Внутри работы её утверждения, прогоны, числа. Разборы статей лежат отдельным репозиторием темы. Никакого отдельного приложения: клонируешь работу, правишь файлы, открываешь предложение о слиянии. Всё остальное — проверки, поиск, доски — надстройки над этим.

Зачем: чтобы на вопрос «а это кто-нибудь уже пробовал» был ответ, и чтобы у числа в статье был адрес, по которому его можно открыть и проверить. Приватное и незрелое остаётся в личных заметках. Сюда попадает проверяемое.

Сейчас внутри: 6 направлений и 24 темы плюс внутреннее про саму базу, 31 работа, 149 утверждений, 319 серий, 923 прогона, 195 выкладок, 654 разобранные статьи, 194 термина в словарях тем.

## Шаг 1. Получить доступ

[@brainlab_server_access_bot](https://t.me/brainlab_server_access_bot) — тот же бот, что выдаёт доступ к серверам, только в личном чате.

1. **«Мой профиль»** — имя, фамилия, кто рекомендует. Без профиля заявка не уйдёт.
2. **«Получить доступ»** → «Серверы и база знаний» → **«База знаний MCP»** → роль → **«Подать заявку»**.
3. Андрей смотрит заявку, и бот присылает всё сразу:

| что | зачем |
|---|---|
| адрес базы | нужен и агенту, и git |
| ключ MCP | чтение и поиск по базе из агента |
| идентификатор `telegram-123…@users.brainlab-ai.com` | твоё имя внутри базы |
| логин на сайте и временный пароль | вход в браузере |
| ключ для git и три строки `export` | им твоя машина ходит в репозитории |

Сохрани идентификатор: его называют, когда дают доступ к работе.

## Шаг 2. Войти на сайт

Открой адрес из сообщения бота, войди логином и временным паролем, смени пароль в Settings → Password. Git работает и с временным паролем, но пароль из телеграма жить долго не должен.

Сайт — это и есть база. В нём видны направления, темы, работы, предложения о слиянии и доски. **Слияние в браузере и есть запись в базу**: служба сверяется с git перед каждым обращением и видит изменение сразу.

На странице любой темы сверху лежит её предмет области: что это за область, какие в ней семейства методов, чем они платят и где ломаются. Это не формальность, а то, с чего стоит начать.

## Шаг 3. Склонировать работу

Клон живёт **на твоей машине** — на ноутбуке, на сервере, где считаешь, или и там и там. Склонировать можно работу, в тему которой у тебя есть доступ, и любую литературу; на чужую закрытую работу git ответит «not found» — это значит «попроси доступ», а не «сломалось».

```bash
curl -fsSL https://raw.githubusercontent.com/brain-lab-research/claude-brainlab/main/scripts/lab \
  -o ~/.local/bin/lab && chmod +x ~/.local/bin/lab

# три строки из сообщения бота, достаточно один раз — они запомнятся
export LAB_GIT_URL=АДРЕС_БАЗЫ
export LAB_GIT_LOGIN=ТВОЙ_ЛОГИН
export LAB_GIT_TOKEN=КЛЮЧ_ДЛЯ_GIT

cd ~/Papers/моя-статья     # папка проекта, рядом с кодом
lab here wsd-muon          # работа ляжет в ./lab-base
```

Полный путь работы знать не надо: `lab here` ищет её по слагу сам. Адрес, логин и ключ сохраняются в `~/.config/brainlab/` с правами `600`, и ключ попадает в один файл, а не в настройки каждого клона.

Нужны сразу все работы, к которым у тебя есть доступ, — клонируй их обычным `git clone` по ссылкам из дерева: отдельной команды под это нет, и она не нужна.

**Ключи ssh настраивать не надо:** машины ходят по HTTPS с токеном.

## Шаг 4. Посмотреть, как разложено

```
<работа>/                         отдельный репозиторий: wsd-muon, lora-muon, dykaf…
├── README.md                     чем работа занята, её утверждения и открытые вопросы
└── claims/H-XXX-001/             утверждение — это папка
    ├── README.md                 что утверждаем и чем это опровергается
    ├── runs/E-XXX-001.md         прогон: настройки, числа, где их проверить
    ├── series/S-XXX-001.md       серия: что проверяли этой группой прогонов и что вышло
    ├── theory/D-XXX-001.md       выкладка с доказательством
    └── figures/F-XXX-001.svg
```

Рядом с работами в той же теме лежит репозиторий `literature`: разборы статей и словарь терминов темы в `literature/glossary/`.

Коды — ярлыки, а не адреса: `H-` утверждение, `E-` прогон, `S-` серия, `D-` выкладка, `F-` рисунок, `R-` измерение. При перенумерации работы они меняются, поэтому в разговоре надёжнее называть путь к файлу.

**Всё стоит на утверждении.** Прогон сам по себе не знание: он опора под утверждением, которое проверяет. Новый прогон на новом масштабе почти никогда не новое утверждение — это ещё одна опора под уже существующим.

Формат страницы никем не предписан. Открой соседнюю работу и сделай похоже.

## Шаг 5. Внести своё

Обычный git:

```bash
cd ~/Papers/моя-статья/lab-base
lab pull                                  # что изменилось и что уже открыто
git checkout -b claim/H-WSD-001           # ветка на утверждение, которое дополняешь
$EDITOR claims/H-WSD-001/runs/E-WSD-042.md
git add -A
git commit -F -                           # заголовок и тело предложения — это коммит
git push -o merge_request.create \
         -o merge_request.assign=<кто сольёт>
lab checks                                # что сказали проверки
```

Правило ветки одно: **одно предложение на утверждение**, ветка `claim/<H-код>`. Push в ветку, по которой предложение уже открыто, входит в него сам: второе заводить не надо.

Тело предложения берётся из сообщения коммита: первая строка — заголовок, остальное — тело. Обёрток над git у нас нет нарочно. У `lab` осталось ровно то, чего git не умеет: найти работу по слагу (`lab here`), положить ключ туда, где git его найдёт, прочитать задачи (`lab tasks`, `lab take`) и вердикт проверок (`lab checks`).

**Слить может только человек.** Твой ключ сливать не может — ни в чужой работе, ни в своей, если ты не ведущий темы. Это проверено: push ветки проходит, попытка слить отвергается. В защищённую `main` не пишет даже админский ключ сервера.

**Когда предложение нужно и как оно должно выглядеть** — отдельным разделом на передней странице базы. Коротко: на любую правку файлов работы, одно на утверждение, в теле обязательны что изменилось, что исчезло и почему, чем проверено; перед отправкой влить `main` и посмотреть `git diff --stat main..HEAD` глазами.

**Поставь себе две вещи одной командой** — и дальше всё идёт само:

```bash
bash docs/lab/install.sh
```

Он положит `~/.claude/rules/lab.md` (как писать в базу — агент читает один раз за сессию), хук начала сессии (где ты, что пришло в `main`, что тебе поручено — только состояние, девять строк) и `lab` в `~/.local/bin`. Спросит адрес базы, ключ и твой логин GitLab — всё это в письме бота. Повторный запуск безопасен.

У всех в лаборатории стоит одно и то же: один файл правил и один хук. Поэтому агент у тебя и агент у соседа понимают базу одинаково.

**Если у тебя накопился проект целиком** — папка с рукописью, логами, заметками и кодом, — его переносит навык `lab-knowledge` из `skills/lab-knowledge/` в этом репозитории. Это единственный навык для этого: было четыре, они делали одно и то же и путали. Он идёт от описи материалов до слитого предложения, раскладывает найденное по утверждениям и честно останавливается, если роли участника в теме ещё нет. Правила, по которым он это делает, лежат одним файлом в справочнике базы — `brainlab/handbook/canon.md`, у каждого правила имя и строка «чем проверяется»; критерии готовности — `references/acceptance.md` рядом с навыком, как должна читаться страница — `references/claim-page.md`.

## Что проверяется само

На каждый push встаёт вердикт и приходит разбор в обсуждение. `lab checks` показывает то же в терминале. Проверок три, и они одни на любую правку:

- **дерево** — прогон лежит в серии, у серии есть вердикт, у утверждения есть чем его опровергнуть, коды не повторяются;
- **числа** — каждое число на странице утверждения и серии встречается в прогонах под ними. Вывод пересказывает опору, а не добавляет к ней цифры;
- **удаления** — исчезнувшая запись названа в теле предложения.

Проверка судит **правку, а не работу целиком**: старый долг работы не мешает записать новый прогон.

Самое частое замечание: **прогон не входит ни в одну серию** — тогда он не попадёт на страницу утверждения. Поставь в шапку прогона `series: S-XXX-001` и заведи страницу серии.

## Задачи и доска

У каждой работы своя доска: `открыто → делается → на проверке → закрыто`. Открытые вопросы работы лежат там задачами — те же, что перечислены в её README.

```bash
lab tasks     # открытые задачи этой работы и ссылка на доску
```

Ярлыки общие на всю лабораторию: `вопрос`, `прогон`, `выкладка`, `текст`, `долг`, `агенту`, `обязательство`, `организация` — род дела; `делается`, `на проверке` — ход. Взял вопрос — поставь `делается`; закрыл — закрой задачу. Колонка доски и есть ярлык, поэтому перетаскивание карточки ничего кроме ярлыка не меняет.

Срок у задачи — обычное поле Due date. Общий срок на несколько задач — веха (Milestones): она одна на всю лабораторию, и на неё может ссылаться задача из любой работы.

**Все задачи сразу**, по всем работам, куда тебя пустили, — в списке задач группы `brainlab`. Задач работ, куда тебя не пустили, там не видно; это тот же доступ, что к файлам.

**Задачи лаборатории**, не принадлежащие ни одной работе — срок, обязательство наружу, организационное, — лежат в отдельном проекте «План лаборатории» со своей доской. Доступ в него даётся отдельно.

**Задача агенту.** Ярлык `агенту` на задаче значит, что её делает агент: он видит такие задачи в начале каждой сессии в этой работе. Отвечает он предложением, а не комментарием.

Доска — про очередь дел, а не про знание. Знание живёт в файлах и меняется слиянием.

## Литература

Разборы статей в репозитории `literature` своей темы правятся **без предложения**, прямо в `main`: разбор статьи — общее знание, и правка в нём не требует чьего-то одобрения. Ворот у этого репозитория нет нарочно.

## Что видно и кто что может

**Войдя, ты видишь дерево и литературу.** Все направления, все темы с их предметом области и все репозитории `literature` — разборы статей и словари терминов — открыты сразу, без всякого членства. Этого хватает, чтобы понять, чем лаборатория занимается, и прочитать её литературу.

**Работы закрыты, но не спрятаны.** Войдя, ты видишь список работ каждой темы: имя, описание и состав с ролями. Внутрь — файлы, задачи, доска, предложения — только участникам: страница работы открывается, а файлы отвечают отказом. Так нарочно: видно, что работа есть и к кому стучаться, а незрелое и неготовое читается не всеми. Гранты закрыты целиком, вместе со страницей, и лежат отдельной группой.

**Доступов два, и они разные.**

**В работу** — чтобы в ней работать. Открой работу и нажми **Request access**: заявка ляжет на саму работу, и решит её тот, кто в ней ведущий. На её странице, в `Manage → Members`, заранее видно, кто в ней и с какой ролью. Доступ в работу соседние работы темы **не** открывает: взяли в одну — видно только её.

**В тему** — чтобы читать все её работы и заводить в ней новые. Просится кнопкой **Request access** наверху страницы темы. Это отдельная заявка: можно сперва войти в одну работу, а тему попросить потом.

| как зовём | в GitLab | в работе | в теме |
|---|---|---|---|
| гость | Guest | видеть её целиком: файлы, задачи, доску. Завести задачу | то же во всех работах темы |
| читатель | Reporter | то же, но читает и приватные проекты, где гость кода не видит | то же во всех работах темы |
| участник | Developer | ветка, push, предложение | то же плюс заводить в теме новые работы |
| ведущий | Maintainer | слияние предложений, решение заявок | слияние во всех работах темы |
| лид | Owner | — | состав темы и её подгруппы |

Отсюда правило, которое стоит знать: **членство и есть доступ**. Уровня «числится, но не читает» в нашей редакции GitLab нет, поэтому в корневую группу лаборатории не добавляют никого — оно наследуется вниз и открыло бы сразу все работы. Что означает каждая роль, написано и на передней странице группы «Люди лаборатории»: это же таблица, замеренная на живой учётной записи.

**Что у тебя уже есть** — видно у себя: [работы](/dashboard/projects) и [темы](/dashboard/groups) в своём кабинете. Ещё точнее — на странице любой работы `Manage → Members`: там и прямые участники, и унаследованные от темы, с ролями.

**Свою работу заводишь сам, но в своей теме.** Заводить работы может участник темы и выше — поэтому, если нужно начать своё, просить надо доступ в ТЕМУ, а не в работу. Получив его, на странице темы жми New project: слаг латиницей, видимость Private. Первый push в пустую работу разрешён нарочно, иначе её нельзя было бы начать. Ворота на неё ставит проход раз в час, так что в первый час её `main` ещё не защищён — это единственное окно, и дальше она живёт как все остальные. Новую **тему** заводит Андрей: подгруппы участник создавать не может.

**В main не пишет никто.** Push в основную ветку запрещён всем, включая администратора сервера. Войти можно только слиянием предложения, и слить можно только зелёное: красный вердикт проверки отказывает слиянию. Сливает ведущий темы или Андрей.

## Агент и MCP

У базы есть MCP — он нужен **для чтения и поиска**: спросить словами «что у нас известно про прогрев», найти статью, посмотреть чужую работу. Писать через него не надо: агент правит файлы в клоне и открывает предложение, как человек.

```bash
claude mcp add --transport http lab-knowledge "$LAB_MCP_URL" \
  --header "Authorization: Bearer $LAB_MCP_TOKEN"
```

Для Codex ключ передаётся именем переменной, поэтому она должна быть видна процессу при каждом запуске — допиши её в `~/.zshrc`:

```bash
codex mcp add lab-knowledge --url "$LAB_MCP_URL" --bearer-token-env-var LAB_MCP_TOKEN
```

Положи рядом с кодом файл `.lab-work` с одной строкой — слагом твоей работы. Тогда агент не выясняет каждый раз, где он, и `lab here` клонирует работу именно в эту папку.

## Прогон пишет код, а не человек

Гиперпараметры, числа, коммит и железо знает только код, который считал. Он их и записывает. В репозиторий с обучением кладётся один файл `lab_run.py` — он лежит в базе, в работе `tools`, только стандартная библиотека, python 3.9+:

```python
from lab_run import LabRun

with LabRun(work="small-vocab", name="vocab8k-seed0", settings=vars(args)) as run:
    for step, batch in enumerate(loader):
        run.metric("train/loss", train_step(batch), step=step)
    run.metric("val/ppl", ppl, step=step, final=True)
    run.where("brain_lab:~/runs/vocab8k-seed0/train.log")
```

Ложится `lab-runs/<имя>.json` с настройками, метриками, версией torch, картой, номером slurm-задачи и коммитом. Падение не теряется: OOM закрывает запись статусом `failed` с причиной.

**У числа обязательно место, где его можно открыть глазами**: страница в W&B, путь к логу, файл прогона. Число, которое нечем проверить, знанием лаборатории не является.

## Если не работает

- **`не знаю адреса базы`** — скажи `export LAB_GIT_URL=…` один раз, адрес в сообщении бота.
- **`работы … не видно`** — слаг набран неточно; `lab` подскажет похожие.
- **git просит пароль** — не сказаны `LAB_GIT_LOGIN` или `LAB_GIT_TOKEN`.
- **`есть свои правки, не трогаю`** — ты не на `main` или есть незакоммиченное. Это не ошибка, а отказ затирать твоё.
- **`You are not allowed to push code to protected branches`** при push без ветки — ты на `main`, сделай ветку.
- **`проверки ещё не проставлены`** — вердикт ставит служба, она ходит раз в минуту. Повтори `lab checks` через минуту.
- **`You are not allowed to push code to protected branches`** — ты пушишь в `main`. Так и должно быть: в `main` входят только слиянием.
- **401 у MCP** — ключ неверен или отозван. Показать заново: `/mcp` у бота.
- **404 на страницу, которая точно есть** — у тебя нет к ней доступа, и GitLab нарочно отвечает так же, как на несуществующую: иначе по разнице ответов перебирается состав базы.

## Куда писать

Андрею, включая мелочи: непонятный отказ, странную выдачу, неработающую ссылку, правило, которое мешает делать работу. База собиралась под то, как работает лаборатория, а не наоборот. Если правило мешает — это, скорее всего, ошибка правила, и вопрос «почему нельзя вот так» ценнее обхода.
