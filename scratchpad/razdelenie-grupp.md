# Shared groups: команда получает доступ сразу ко всем своим темам

Владелец 07-10-2026: «давай подумаем над share groups… если группа разработчиков матричной
оптимизации, им как-то сразу появляется доступ к отдельным проектам».

Ниже только измеренное состояние и предложение. Ничего не заведено: любое разделение
требует роли ведущего, которой у агента нет.

## Что есть сейчас

| | |
|---|---|
| людей с входом в базу | 24, все в группе `people` |
| членство в `people` | ничего не открывает, это просто список заведённых |
| доступ к теме | даётся приглашением в саму тему, человеку поимённо |
| разделений группы с группой | **ноль**, ни одного во всём дереве |
| групп вне лаборатории | три: `people`, `ops`, `grants` |

Правило, которое действует: доступ даётся на тему, а не на лабораторию. Дерево и
литература открыты всем заведённым, работы закрыты.

## Чем плохо поимённо

Человек приходит в матричную оптимизацию — его надо позвать в семь тем по отдельности:
`muon-adaptive-preconditioning`, `muon-sign-methods`, `muon-at-scale`,
`muon-convergence-theory`, `non-euclidean-dependent`, `preconditioning-curvature`,
`training-dynamics`. Семь приглашений, семь мест, где можно забыть.

Человек уходит — те же семь мест надо обойти снова. Забыли одно, и у него остаётся доступ,
о котором никто не помнит. Это не гипотеза: именно так расходятся списки доступа везде,
где их ведут вручную.

## Предложение: команда — это группа, и она разделяется с темой

Команды заводятся подгруппами внутри `people`, рядом с её смыслом «список заведённых»:

```
people/matrix-optimization      кто работает по матричной оптимизации
people/low-rank                 кто работает по низкоранговым методам
people/zero-order               кто работает по безградиентной оптимизации
```

Дальше команда разделяется с темами своего направления, по одному вызову на тему:

```
POST /groups/<тема>/share   { group_id: <команда>, group_access: 30 }
```

После этого:

- **один человек — одно место.** Завели в `people/matrix-optimization`, и у него сразу
  есть все семь тем направления. Убрали оттуда — и нет ни одной;
- **видно, кто за что отвечает.** Список команды и есть ответ на вопрос «кто у нас по
  матричной оптимизации», и его не надо собирать обходом тем;
- **правило «доступ на тему» не ломается.** Разделение идёт с темой, а не с корнем
  лаборатории: команда низкоранговых методов не получает матричную оптимизацию;
- **роль задаётся один раз.** `group_access: 30` — разработчик: пушить ветки можно,
  сливать в защищённую основную нельзя, это остаётся за ведущим темы.

## Чего это не решает, и об этом надо знать заранее

**Один человек в двух направлениях** состоит в двух командах, и доступ у него
объединённый. Это и нужно, но тогда «чем человек занят» перестаёт читаться одной строкой.

**Гость в одной теме направления** через команду не выражается: команда даёт всё
направление. Такого зовут поимённо, как сейчас, и это нормально — команда для постоянных,
приглашение для разовых.

**`.lyudi.json` остаётся отражением GitLab, а не источником.** Если команды появятся,
проход, который его собирает, должен читать и членов темы, и членов разделённых с ней
групп, иначе он будет показывать меньше, чем есть на самом деле. Это правка в проходе, и
её надо сделать ДО того, как заведём первую команду, иначе картина доступа разойдётся с
действительностью молча.

**Ключ группы `group_2_bot_*`** — живой бот выдачи доступа. Любая возня с членством групп
не должна его трогать.

## Что сделать, когда будет решение

1. Поправить сбор `.lyudi.json`: читать членов темы плюс членов разделённых групп.
2. Завести три команды подгруппами `people`, по одному направлению на пробу.
3. Разделить команду матричной оптимизации с её семью темами.
4. Проверить вживую одним человеком: завести в команду, убедиться, что видит все семь тем
   и не видит низкоранговые; убрать и убедиться, что не видит ничего.
5. Только после этого переносить остальные направления.

Пункт 4 обязателен. Права — ровно тот случай, где «должно работать» и «работает» часто
расходятся, а цена ошибки — чужие данные.
