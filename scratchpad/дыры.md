# Дыры перед раскаткой на лабораторию

Снято 29-09-2026 проверкой вживую, не рассуждением. Каждая строка либо воспроизведена
вызовом, либо получена обходом кода — где не проверено, так и написано.

## Закрыто сегодня

**Служба не видела слияний.** База читалась один раз, при запуске. Человек сливал pull
request, а служба продолжала отвечать по своей копии и строить из неё чужие ветки.
Закрыто: перед каждым обращением сверяется состояние git по файлам ссылок, изменился —
перечитываем. Проверено вживую: запись, появившаяся в `main`, видна сразу, исчезновение
тоже.

**Предложение агента сносило файлы за пределами своей правки.** Ветка приводилась к
виду «вся работа как её видит служба», и всё, чего рендер не выдаёт, удалялось. На
wsd-muon предложение с ОДНИМ прогоном удаляло девять файлов: восемь рисунков и
`captions.json`. Закрыто двумя ограничениями: удаляются только `.md` и только внутри
каталогов тех утверждений, которых предложение касается.

**Путь `propose` не работал вовсе.** Под git-хранилищем не было ни `find_user`, ни
хранилища предложений — они остались только у Postgres. Агент не мог записать ничего, а
снаружи это выглядело как работающие ворота. Закрыто, проверено сквозняком: propose →
ветка `claim/H-WSD-001` → pull request → статус проверки.

## 1. Тринадцать методов хранилища отсутствуют под git

Каждый падает в свой момент, у своего человека, с сообщением про внутреннее имя класса.

| инструмент MCP | чего не хватает | что человек не сможет |
|---|---|---|
| `who_works_on_what` | `people_workload` | узнать, кто чем занят |
| `lab_health` | `stalled_work` | спросить базу о её состоянии |
| `recent_changes` | `changes_since` | увидеть, что изменилось за неделю |
| `get_timeline` | `entity_timeline` | посмотреть историю утверждения |
| `get_related` | `related_entities` | найти связанное с записью |
| `related_by_terms` | `records_sharing_terms`, `papers_sharing_terms` | найти по смыслу |
| `browse_by_subject` | те же плюс `repositories_sharing_terms`, `count_records_sharing_terms` | «что у нас есть про X» |
| `library_tree` | `library_tree` | увидеть форму библиотеки |
| `find_skill`, `list_skills`, `upsert_skill` | одноимённые | работать со скиллами |

**Как закрыть.** Дописать эти методы в `MemoryRepository` — они все механические:
перебор словарей в памяти вместо SQL. Так уже сделано сегодня для `find_user`,
хранилища предложений, `records_by_public_code` и `link_decision_hypotheses`.
Ориентир: полдня на все тринадцать вместе с проверками. Порядок по важности для
раскатки: `lab_health` и `recent_changes` (без них не видно состояния базы), потом
`who_works_on_what`, потом связи и библиотека, скиллы последними.

**Как не допустить снова.** Завести проверку, которая перебирает вызовы
`repository.<метод>` по всему коду службы и падает, если метода нет у `MemoryRepository`.
Скрипт для этого уже написан и лежит в черновиках сессии — его надо оформить тестом,
иначе следующий метод, оставшийся от Postgres, найдётся снова у человека, а не у нас.

## 2. Доступ к работе нельзя выдать через MCP — ЗАКРЫТО 29-09-2026

`invite_member` заводит человека, `issue_agent_token` даёт ключ, а права на работу
выдаются только правкой `.lyudi.json` на сервере. Значит каждый новый участник ждёт
того, у кого есть доступ к серверу.

Сейчас: 18 учётных записей из 23 не имеют ни одной работы. Они видят базу, но не могут
ни писать, ни предлагать — право на работу проверяется раньше, чем «агент ли ты».

**Закрыто.** `grant_project` и `revoke_project` выведены наружу: почта, слаг работы,
роль. Зовёт ведущий работы или ведущий лаборатории; агент получает отказ — раздача
доступа не его дело. Выдача пишется в файл доступа атомарно, с правами 600, иначе она
жила бы до перезапуска. Проверено вживую: выдал, перезапустил службу, отозвал — файл
обновился в обе стороны.

**Оговорка, которая меняет срочность.** Участник может **завести свою работу сам** —
проверено: `create_project` отработал, участник становится её ведущим и пишет в неё
напрямую. То есть новому человеку не нужен чужой грант, чтобы начать: он нужен только
чтобы войти в ЧУЖУЮ работу.

## 3. Заведение работы стоит вне ворот — ЗАКРЫТО 29-09-2026

Проверено: агентский ключ завёл работу одним вызовом, без pull request, и стал её
ведущим. Ворота на записи держат — утверждение в свою же работу агент написать напрямую
не смог, — но саму работу завёл молча.

Это ровно тот случай, которого ты опасался: один невнимательный человек или агент
насыпает в базу работ, и убирать их придётся руками.

**Закрыто.** Агенту отказано так же, как на записи утверждения: работа это папка в общей
базе, и решает человек. Проверено на живой службе: агентский ключ получает отказ, человек
заводит работу и становится её ведущим.

## 4. Модель не знает про рисунки

Рисунки кладёт отдельный проход, служба про них не знает вовсе. Сегодня она их больше не
уничтожает, но и перенести не может: при перенумерации утверждения страницы уедут в новый
каталог, а `figures/` останется в старом сиротой. Не проверено вживую, выведено из кода.

**Как закрыть.** Сделать рисунок записью базы наравне с прогоном: код `F-`, подпись, к
какому утверждению относится. Тогда перенумерация и перенос тронут его вместе со всем
остальным. Два-три дня, потому что придётся переносить 179 существующих файлов.

## 5. Административные команды не работают под git

`admin.py` зовёт `repository._connection()` — это соединение с Postgres. Под git-хранилищем
падает всё, что идёт через него.

**Как закрыть.** Заменить проверку «есть ли пользователи» на вызов, который есть у обоих
хранилищ. Час.

## 6. Поиск не работает

Отложен тобой сознательно: `search()` честно отказывает вместо того, чтобы врать. Держу
в списке, чтобы это не выглядело забытым.

## 9. Два предложения в одно утверждение теряли запись — ЗАКРЫТО 30-09-2026

Правило «один pull request на утверждение, много коммитов» на деле теряет записи.
Проверено на H-LKP-001: первое предложение добавило прогон `E-LKP-005`, второе,
сделанное до слияния, получило **тот же код** и молча переписало его. В ветке остался
только второй прогон, первый исчез.

Причина: свободный код считается по тому, что служба знает из `main`. Записи, лежащие
в ветке предложения, в этот счёт не входят — модель их не видит, потому что они ещё не
слиты.

**Чем опасно.** Это ровно тот ход работы, который правила и поощряют: агент неделю
дописывает корпус в один PR. Каждая следующая дописка затирает предыдущую, а в
интерфейсе это выглядит как обычный коммит «изменён файл».

**Настоящая причина оказалась глубже.** Предложения живут в памяти службы и не переживают
перезапуск. После него соседнее предложение исчезает, и дальше ломается дважды: номер
выдаётся тот же, а запись прошлого захода вдобавок удаляется как «лишняя» — рендер её не
выдаёт, потому что не знает о ней.

**Закрыто двумя правками.** Занятые коды считаются по дереву самой ветки, а не только по
`main`: имя файла и есть код, у утверждения — имя каталога. И в уже открытой ветке
удаление запрещено вовсе: она копится неделями, а память службы — нет, поэтому «лишним»
там оказывается ровно то, что положил предыдущий заход.

Проверено вживую дважды, каждый раз с перезапуском службы между предложениями: сперва
номер перестал затираться, потом перестала пропадать и сама запись.
