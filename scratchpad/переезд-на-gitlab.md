# Переезд с Gitea на GitLab — план

Решение принято 30-09-2026. Причина не «GitLab лучше», а две вещи, которых у Gitea нет
и не будет:

1. **Дерево групп.** Направление → тема → проект. У Gitea одна плоская организация;
   спросил её собственное описание API: 308 путей, 34 про организации, про вложенность и
   подгруппы — ни одного, и у объекта организации нет поля «родитель».
2. **Доска задач через API.** В описании API Gitea 0 путей про доски. Доски есть в
   интерфейсе, но агент их не тронет, а канбан нужен именно агентам. Костыль на метках
   владелец отверг прямо: «делать костыльный через гитею канбан мы не будем».

Всё остальное — репозитории, ветки, pull request, права, защита ветки, статусы проверок —
у обоих есть, и ради этого переезжать было бы незачем.

## Что измерено, а не оценено

```
клиент gitea.py            380 строк, 10 вызовов API
зовут его                  3 файла, ~30 мест, через один объект
     service.py 6, pr_watch.py 1, mcp_server.py 1
база читает репозитории    прямо с диска, по имени каталога
```

Десять вызовов, которые надо повторить на GitLab:

```
POST   contents                      записать файлы одним коммитом
GET    pulls                         открытые предложения
POST   pulls                         открыть предложение
GET    pulls/{n}                     прочитать одно
PATCH  pulls/{n}                     переписать тело питча
POST   pulls/{n}/update              подтянуть основную ветку
POST   issues/{n}/comments           комментарий
POST   statuses/{sha}                поставить галочку проверки
GET    commits/{sha}/statuses        прочитать галочки
DELETE branches/{имя}                убрать ветку
```

У GitLab всё это есть один в один, только другими адресами: `repository/commits`,
`merge_requests`, `notes`, `statuses`, `repository/branches`.

## Узкое место, найденное при разборе

**База читает голые репозитории с диска по имени.** Так она грузит 33 работы, 645
разборов литературы и словари за секунды — одним `git cat-file --batch` на репозиторий.

У GitLab так нельзя. Хранилище хешированное (`@hashed/b1/7e/b17ef6…git`, SHA256 от id
проекта), по имени не найти, а прямой доступ к каталогу объявлен устаревшим: полагается
ходить через Gitaly.

**Решение — зеркальные клоны.** На каждую тему `git clone --mirror`, рядом служба
периодического `fetch`. Тогда `gitstore` не меняется вовсе, меняется только корень в
`LAB_KNOWLEDGE_GIT_ROOT`. Ходить по API вместо диска нельзя: это сотни запросов на одну
загрузку вместо одного процесса.

## Порядок работ

**0. Развернуть GitLab рядом, ничего не выключая.** Gitea продолжает работать, MCP
продолжает читать её. Пока не сделано: **у меня нет прав** — docker на brain_lab есть
(29.1.3), но пользователь `shkodnik1917` к сокету не допущен, root и sudo нет. Нужно либо
добавить его в группу `docker`, либо развернуть контейнер руками владельца. Занятые порты:
80, 3000, 3080, 8000, 8001, 8080, 8081, 8082, 8086, 8088, 8443, 8787, 8788, 8799.

**1. Перенести содержимое.** У GitLab есть встроенный импортёр из Gitea: репозитории,
задачи, pull request, вехи, метки, заметки к диффам. Две оговорки:
- **вики импортёр не переносит**, а там словари имён — 186 записей. Вики это тоже git,
  поэтому переносятся `push`ем вручную;
- авторство теряется, всё достаётся импортирующему. Нам почти всё равно: предложения
  открывает `lab-agent`.

**2. Переписать клиент.** Новый `gitlab.py` с тем же интерфейсом, что `gitea.py`: тогда
`service.py`, `pr_watch.py` и `mcp_server.py` не трогаются вовсе. День.

**3. Зеркала.** Клон на тему плюс `fetch` по расписанию, `LAB_KNOWLEDGE_GIT_ROOT` на них.
Полдня.

**4. Права и защита заново.** Группы по направлениям, проекты внутри, защита основной
ветки, списки сливающих, открытый путь для литературы. В Gitea это сделано и проверено —
повторить по тому же списку.

**5. Переключить и проверить сквозняком.** Тот же прогон за нового участника, что
проходили 29-09: приглашение, ключ, работа, утверждение, ключ агенту, отказы агенту,
предложение, merge request, проверка, слияние. Четырнадцать шагов.

**Оценка: 2–3 дня работы.** Не недели, как я сказал сначала, — сцепка оказалась в один
объект на 380 строк.

## Чего переезд НЕ чинит

- предложения по-прежнему живут в памяти службы и не переживают перезапуск;
- рисунки по-прежнему вне модели;
- долг работ, поиск, поле почты в боте — всё это платформы не касается.

## Что появится после переезда

- дерево направление → тема → проект, которым можно ходить;
- канбан, которым управляют агенты, и задача, связанная с предложением напрямую;
- права на проект, а не на тему: предложение идёт в проект.

## Третий довод: заявка на доступ (30-09-2026)

Владелец хочет, чтобы участник сам выбирал работы на сайте, а ведущий его принимал:
«изначально у них ничего не доступно, доступно только описание проектов и литература,
а потом они тыкают на кнопки, типа хочу сюда, и их уже лид определяет в проекты».

Проверено по бинарнику Gitea 1.27.3: **в Gitea такого механизма нет**. Строк
`access request`, `Request to join`, `join_request` нет вовсе; два вхождения
`request_access` — это `json:"request_access_enabled"` в её клиенте GitLab API, то есть
в импортёре. Членство выдаётся только приглашением со стороны организации.

Оттуда же следует, что **в GitLab это штатное поле проекта и группы**:
`request_access_enabled`. То есть кнопка «Request Access» и одобрение ведущим — не
доработка, а настройка.

Итого доводов за переезд три: канбан, отсутствие рабочего процесса выдачи доступа,
и вот эта заявка на присоединение. Против — хешированное хранилище (`@hashed/xx/yy/…`)
и импортёр, который не переносит вики.

Пока не переехали: участник видит все открытые работы и пишет владельцу в личку.
