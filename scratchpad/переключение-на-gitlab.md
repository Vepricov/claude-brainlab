# Переключение базы с Gitea на GitLab

Состояние на 01-10-2026: GitLab готов и проверен, живая база по-прежнему читает Gitea.
Переключение — девять шагов, каждый проверяемый, откат везде обратный.

Адрес GitLab снаружи: `https://68-183-24-188.sslip.io:9445` (TLS снимает Caddy на do-vpn,
туннель `brainlab-gitlab.service`, порт 9445 открыт в ufw).

## Перед переключением

Слить в Gitea то, что висит: pull request #2 в `lab-agents`. После переключения Gitea
перестанет быть базой, и несделанное слияние останется несделанным.

## Шаги

1. **Догнать разницу.** Gitea живая и продолжает принимать статьи, поэтому перед
   переключением:

   ```bash
   cd ~/brainlab-stack/lab-knowledge/scripts
   set -a; . ~/brainlab-stack/gitlab/.mirror.env; set +a
   python3 gitlab_delta.py            # показать
   python3 gitlab_delta.py --apply    # дослать литературу
   python3 gitlab_delta.py            # должно сказать «разницы нет»
   ```

   Работы здесь не досылаются нарочно: запись в работу идёт только слиянием. Если
   `gitlab_delta.py` показал расхождение в работе — значит в Gitea слили что-то после
   переезда, и это нужно внести в GitLab отдельным предложением, а не проходом.

2. **Остановить запись в Gitea.** Иначе после переключения в неё будут писать службы, и
   записи потеряются:

   ```bash
   systemctl --user stop lab-knowledge-pr-checks.service lab-knowledge-mirror.service
   ```

3. **Служба базы читает зеркала GitLab и пишет в GitLab.** В `.service.env`:

   ```
   LAB_KNOWLEDGE_GIT_ROOT=/home/shkodnik1917/brainlab-stack/mirror-gitlab
   LAB_KNOWLEDGE_GIT_KIND=gitlab
   LAB_KNOWLEDGE_GIT_URL=http://127.0.0.1:9080
   LAB_KNOWLEDGE_GIT_PUBLIC_URL=https://68-183-24-188.sslip.io:9445
   LAB_KNOWLEDGE_GIT_TOKEN=<ключ GitLab, он же в gitlab/.mirror.env>
   LAB_KNOWLEDGE_GIT_REPO=brainlab/lab-agents/lab-knowledge-pipeline
   ```

   ```bash
   systemctl --user restart lab-knowledge-user.service
   ```

   Проверка: `lab_health` и число утверждений — должно быть 149, как в Gitea.

4. **Бот заводит учётки в GitLab.** В `.service.env` добавить `LAB_ACCESS_SITE=gitlab`
   (ключ `LAB_GITLAB_TOKEN` там уже есть) и перезапустить службу базы. Проверка: выдать
   доступ одному человеку и посмотреть, что в сообщении есть логин, временный пароль,
   адрес и три строки `export`.

5. **Помощник участника.** `scripts/lab-gitlab` становится `scripts/lab`, прежний
   удаляется:

   ```bash
   cd ~/Staff/BRAIn\ Lab/claude-brainlab && git mv scripts/lab-gitlab scripts/lab
   ```

   Единица в нём — работа, а не тема: `lab here wsd-muon`, не `lab here training-dynamics`.

6. **Хук начала сессии.** `~/.claude/hooks/lab-where-am-i.py` зовёт `lab here <тема>` и
   читает Gitea. Переписать на работу и на GitLab: клон работы, её задачи, её предложения.

7. **Адрес и ключ на машинах.** У каждого в `~/.config/brainlab/`: `git-url` на новый
   адрес, `git-token` — ключ GitLab. Ключ машины выдаётся так:

   ```bash
   python3 gitlab_keys.py выдать <метка машины>
   ```

8. **`create_project` в MCP считает, что работа — папка в репозитории темы.** В новой
   раскладке это не так, и после переключения инструмент либо заводит работу проектом в
   GitLab, либо убирается. Пока он есть, работу надёжнее заводить на странице темы кнопкой
   New project: проверено, участник это может, и работа рождается под воротами.

9. **Правила.** `~/.claude/rules/lab-git-literature.md` описывает Gitea, репозиторий на
   тему и `литература/<ключ>.md`. В GitLab работа — проект, литература — отдельный проект
   темы, словари лежат файлами в `literature/glossary/`.

10. **Погасить Gitea.** Не раньше, чем неделя на GitLab прошла без сюрпризов:

   ```bash
   systemctl --user stop gitea-user.service
   systemctl --user disable gitea-user.service
   ```

   Данные не удалять: `~/brainlab-stack/gitea` и `~/brainlab-stack/mirror` остаются как
   точка отката.

## Откат

Обратно: `LAB_KNOWLEDGE_GIT_ROOT` на `mirror`, `LAB_KNOWLEDGE_GIT_KIND=gitea`,
поднять две остановленные службы, вернуть `scripts/lab`. GitLab при этом не ломается и
может стоять рядом сколько угодно.

## Что проверено делом, а не прочитано в документации

- Красный вердикт проверок **запрещает** слияние (405), зелёный пропускает. Включается
  свойством проекта `only_allow_merge_if_pipeline_succeeds`; сейчас выключено, потому что
  это решение владельца, а не моё.
- В защищённую `main` **не пишет даже админский ключ** (403). Войти можно только слиянием.
- Участник пушит ветку в любую работу и открывает предложение, но слить не может (401).
  Ведущий своей темы — может, в своей теме.
- Видимость `internal` даёт чтение всей базы без единой записи о членстве; `grants`
  остаётся закрытой группой и не виден вовсе (404, а не отказ).
- Заявка на доступ работает: постучался — виден в `gitlab_requests.py список` — одобрен —
  стал разработчиком.
- Клон и push по публичному адресу ключом группы работают с ноутбука.

## Грабли, которые уже стоили времени

- **Кириллическая метка проекта принимается кодом 200 и выбрасывается без следа.** Метки
  только латиницей; `gitlab_cards.py` сверяет их после записи.
- **Имя группы или проекта с двоеточием или запятой отвергается.** Обрезается по первому
  такому знаку (`gitlab_api.годное_имя`).
- **Список ветвей у API кэшируется.** После удаления ветка ещё видна; правду говорит
  `git ls-remote`.
- **GitLab считает дифф предложения не сразу.** Сразу после открытия «правка ничего не
  задевает» — это не ответ, а незаполненный кэш.
- **`http_url_to_repo` показывает внешний адрес.** Подстановка ключа в него перестала
  работать в тот момент, когда GitLab вывели наружу, и перестала молча.
- **Перенос `gitlab_move.py` повторно не проходит**: раскол и main разошлись, push
  отвергается как не-fast-forward. Разницу догоняет `gitlab_delta.py`.
- **Туннель цеплялся к общему ssh-соединению** и потому отваливался; нужен
  `-o ControlMaster=no -o ControlPath=none`.

## Ещё одна ловушка, найденная при проверке

Защита, пришедшая из умолчания группы, **не видна в списке защищённых ветвей проекта**:
`/projects/:id/protected_branches` отвечает пустотой, а push в `main` при этом отвергает
pre-receive. Судить о воротах по этому списку нельзя — только попыткой записи.
