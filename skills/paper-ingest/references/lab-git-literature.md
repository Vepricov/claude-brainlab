# Литература и git лаборатории (applies to ALL agents, ALL sessions)

Общая база знания лаборатории живёт в git. С 01-10-2026 это **GitLab**:
`https://68-183-24-188.sslip.io:9445`, дерево групп направление → тема → работа. **Работа —
отдельный репозиторий**, литература темы — отдельный репозиторий `literature` рядом с
работами, словарь темы — файлы в `literature/glossary/`.

Ключ машины лежит в `~/.config/brainlab/git-token`, логин агента в `git-login`, свой логин
в `gitlab-login`, адрес в `git-url`; личным ключом человека не ходить. Ключ выдаёт
`gitlab_keys.py выдать <логин> <метка машины>` — это личный ключ учётной записи агента
`<логин>-agent`, она состоит там же, где человек, но не выше разработчика: пушит ветки и
открывает предложения, слить не может нигде.

Устройство репозитория темы:

```
<работа>/                     отдельный репозиторий
├── README.md                 работа, её утверждения и открытые вопросы
└── claims/H-XXX-001/         утверждение, серии, прогоны, выкладки, рисунки

<тема>/literature/            отдельный репозиторий рядом с работами
├── <citation_key>.md         разбор статьи целиком
├── glossary/<термин>.md      словарь темы
└── _attachments/             рисунки к разборам
```

Предмет области темы лежит не в репозитории, а передней страницей её группы
(`<тема>/gitlab-profile/README.md`, проект держится в архиве). Его источник — файл
`services/lab-knowledge/scripts/gitlab_pages/themes/<тема>.md`, и правится он там.

## Ингест статьи не закончен, пока страница в git неполная

`paper-ingest` и `want-2-read` доводят статью до Zotero, хранилища и корпуса. Этого мало:
страница `литература/<ключ>.md` создаётся службой из корпуса и печатает **только краткое
изложение**, а разделы разбора остаются в базе невидимыми. Поэтому после шага синхронизации
с корпусом обязателен ещё один:

```bash
python3 ~/.agents/skills/paper-ingest/scripts/lab_page_sync.py --arxiv <ARXIV_ID>
```

Скрипт дописывает в страницу разделы из корпуса, переносит рядом рисунки, на которые они
ссылаются, и переводит рисунки из PDF в PNG: иначе GitLab их не показывает. Проверить можно
`--dry-run`. Одной командой чинится и вся тема: `--theme <слаг>`.

Признак невыполненного шага: на странице статьи один заголовок `## Про что работа` и больше
ничего, при размере около трёх килобайт.

**База доступна по сети, туннель больше не нужен.** GitLab слушает снаружи, ходить к нему
надо по адресу из `~/.config/brainlab/git-url`, заголовком `PRIVATE-TOKEN` и ключом из
`git-token` (права `600`, свой у каждой машины). Сертификат самоподписанный, поэтому проверка
цепочки отключается осознанно — адрес берётся с диска, а не из сети.

Три отличия, каждое из которых ломает старый код молча:

- авторизация заголовком `PRIVATE-TOKEN`, а не `Authorization: token`;
- у темы **отдельный проект** `literature` внутри её группы, а не папка `literature/` в
  репозитории темы — путь вида `brainlab/<направление>/<тема>/literature`;
- страницы лежат в **корне** проекта: `<citation_key>.md`, а не `literature/<ключ>.md`.

Полный путь проекта у каждой темы свой, потому что направления разные
(`zero-order/zo-estimators`, `large-models/llm-scaling`), и его надо искать в списке проектов,
а не собирать из слага.

**Читать базу целиком дорого.** Одна страница это один запрос, и обход всех 651 занимает
полчаса. Дерево проекта отдаёт хеш каждого файла бесплатно, поэтому `lab_pull.py` держит
кеш `~/.config/brainlab/pages-cache.json` и перечитывает только изменившееся. Кеш
регенерируемый: удалить безопасно, следующий проход соберёт заново.

Рисунки при этом лежат по-разному: у владельца в хранилище, на сервере в
`/root/paper-agent/state/_attachments`. Скрипт ищет в обоих местах, а перекрыть список можно
переменной `BRAINLAB_FIG_ROOTS`. Если вложений на машине нет вовсе, вики-вставка остаётся как
была, чтобы её перевёл прогон оттуда, где рисунки есть.

Серверный конвейер закрывает шаг сам: `ingest_finish.py` вызывает `lab_page_sync.py` сразу после
отправки в корпус. Шаг необязателен для закрытия очереди — git это зеркало, и при лежащем туннеле
статья всё равно уже в корпусе, но в журнал уходит строка о неудаче.

Подмести всё, что накопилось, можно одной командой:

```bash
python3 ~/.agents/skills/paper-ingest/scripts/lab_page_sync.py --fill-thin
```

Она проходит все темы и дополняет страницы, где напечатано только краткое изложение. Безопасна
для повторного запуска: страницу, которая уже полная, она не трогает.

## Правки README темы переживают проходы, но только README

С 27-09-2026 публикация больше не перезаписывает файлы репозитория, она только заводит
недостающие. Поэтому README темы и страницы литературы можно править, и правка живёт.
Проверять это надо по файлам коммита, а не по имени автора: проход службы `lab-knowledge`
коммитит и свои файлы работ, и это не откат.

## Статьи, которые появились в базе без владельца

Другие участники добавляют статьи в свои темы. **Локально они сами не появляются и не должны.**
Владелец решает, брать ли их. Инструмент показывает разницу и приносит выбранное:

```bash
python3 ~/.agents/skills/paper-ingest/scripts/lab_pull.py --list
python3 ~/.agents/skills/paper-ingest/scripts/lab_pull.py --list --theme latent-reasoning
python3 ~/.agents/skills/paper-ingest/scripts/lab_pull.py --pull <citation_key>
```

`--pull` кладёт разбор в `Literature/_inbox` с вики-ссылками и скачанными рисунками, и на этом
останавливается: перенос в папку темы — действие владельца, как и для карточек «Инбокса» на
доске чтения. Флаг `--into-theme` есть, но применяется только по прямой просьбе.

**Выбирать вручную больше не нужно.** `lab_pull.py --sync` привозит в `_inbox` всё, чего нет
локально, целиком — с разбором, формулами и рисунками, потому что страница в базе теперь полная.
С 29-09-2026 это делает служба `ru.brainlab.literature-sync` каждые три часа, журнал в
`~/Library/Logs/brainlab/literature-sync.log`. Темы для обхода берутся из базы, а не из локальных
папок: тема может появиться без владельца. Репозитории, которые не являются темами литературы
(`grants`), перечислены в `NOT_A_THEME`.

**Корзина.** Статью, которая не нужна, владелец перетаскивает из `_inbox` в `Literature/_trash`.
Следующий проход `--sync` заносит её в журнал отказов `_trash/paper-search_rejected.md`, удаляет
заметку вместе с вложениями и больше её не приносит. Из базы при этом ничего не удаляется: там
статья принадлежит тому, кто её добавил, и решение выкинуть её локально — только локальное.

Сравнение идёт по номеру arXiv, но у части страниц вместо номера стоит слаг AlphaXiv вроде
`2609.deepseek-v4-1-flash`. Для них сверка идёт по названию, иначе один и тот же разбор приезжал
бы каждый проход.

Сравнение идёт по номеру arXiv, а не по названию: названия в базе и в файле расходятся
(двоеточия, формулы, длина), и по ним получается ложная разница.

## Рисунки, нарисованные в TikZ, копированием не извлечь

Из исходников arXiv шаг извлечения берёт файлы, на которые ссылается
`\includegraphics`. Рисунка, нарисованного прямо в TikZ или pgfplots, файла не имеет:
он вычисляется при сборке. Такие рисунки молча пропадают, и в разборе остаётся текст
«по данным Figure 2» без самой Figure 2. У 2609.38095 так потерялись четыре рисунка из
двенадцати, включая обзор метода — а на его место встал авторский игрушечный пример,
и это выглядело как самодельная картинка.

Проверка простая: сколько в исходнике окружений `figure` и сколько файлов скопировано.
Разошлось — значит часть нарисована в коде.

```bash
python3 ~/.agents/skills/paper-ingest/scripts/tikz_render.py <каталог исходников> <куда> fig:метка ...
```

Скрипт берёт преамбулу статьи целиком (построчная выборка ломает многострочные
`\newcommand`), убирает класс статьи и стиль конференции, собирает окружение классом
`standalone` и переводит в PNG. LaTeX есть и у владельца, и на do-vpn.

Если сборка не идёт — не хватает стиля, данные к графику лежат отдельным файлом, —
есть запасной путь: вырезать рисунок из опубликованного PDF по подписи,
`crop_figures.py <pdf> <куда> "2=Comparison of 1SPSA"`. Он аккуратнее, чем
`extract_pdf_figures.py --vector`: ширину задаёт сама графика, поэтому в кадр не
попадает соседняя колонка текста. Вторая половина аргумента — первые слова подписи из
исходника: в PDF рядом с настоящей подписью бывает короткое описание для доступности,
тоже начинающееся с «Figure N.», и без сверки по тексту берётся не тот рисунок.

## Четвёртое место: Zotero тоже на темах

С 30-09-2026 Zotero больше не исключение. Прежняя вложенная таксономия
(`Optimization/zero-order`, `PEFT/lora_base`, `LLM/scaling_laws`) снесена, вместо неё одна
коллекция `Literature` и в ней двадцать четыре коллекции с теми же слагами, что репозитории
тем в базе, папки `Literature/<тема>` в хранилище и папки `personal/<тема>` на AlphaXiv.
620 статей разложены по теме их страницы в базе, а не по имени прежней коллекции. Проектные
коллекции `Research-*` и партии `_inbox/w2r_*` не тронуты: они не про литературу.

Из этого следует, что файла соответствия темы коллекции больше нет и заводить его снова не
надо. `theme_to_zotero.json` держал двадцать пять строк, из которых шесть были догадкой по
смыслу, и по такой строке статья уезжала не в ту коллекцию молча. Теперь
`zotero_web.py` просто печатает `Literature/<слаг>`.

Пишем Zotero только Web API (`/root/paper-agent/zotero_web.py`, `zotero_retheme.py`), а не
правкой `zotero.sqlite`: у библиотеки включена синхронизация под учётной записью `shkodnik`,
и правка базы мимо приложения ломает её версии. Удаление коллекции в Zotero статьи не
удаляет, они остаются в библиотеке, — поэтому снос пустой таксономии безопасен, но пустоту
надо сперва проверить, а не предположить.

## Статья из базы приезжает с предложенной темой

`lab_pull.py --sync` кладёт в `Literature/_inbox` заметку, у которой в шапке стоит
`предложенная тема` — та, где её страница лежит в базе. Это не догадка, поэтому и решение
принимается одним движением:

```bash
python3 ~/.agents/skills/paper-ingest/scripts/lab_pull.py --accept        # всё
python3 ~/.agents/skills/paper-ingest/scripts/lab_pull.py --accept zheng2025soft
```

Приёмка переносит заметку в `Literature/<тема>/` вместе с рисунками, правит вики-вставки,
добавляет статью в ту же тему на AlphaXiv и заводит её в коллекции `Literature/<тема>` в
Zotero. Заметку, перетащенную в папку темы руками, следующий `--sync` доводит до того же
состояния сам: признак — строка `источник: база лаборатории` есть, `принято:` нет, а лежит
она уже не в `_inbox`. Заметку с таким же именем в теме приёмка не затирает, а оставляет в
`_inbox` и говорит об этом.

## Искать по базе — по дереву, не вызовом

Статью искать по дереву тем в GitLab или по локальной копии хранилища. Пустой ответ
инструмента не значит, что статьи нет. Шаг «спросить общий корпус» в `paper-ingest` делает
`sync_to_lab.py --verify`.

## Коды берутся из клона

```bash
cd <клон работы>
ls claims                                  # коды утверждений, как они есть
find . -name '*-WSD-*' | grep -o '[HDSEF]-WSD-[0-9]*' | sort -u
```

Подставить буквы своей работы и взять по каждому префиксу **наибольший** номер, а не
количество: дыры в нумерации настоящие, и счётчик даёт занятый код. Проверено сличением
клона и базы на `wsd-muon` 01-10-2026: совпало код в код.

Адрес записи — **путь файла в репозитории**. Публичный код остаётся ярлыком для чтения: при
перенумерации работы `H-DYC-035` стал `H-DYC-007`, и код, вписанный в текст страницы, после
такого надо править, а путь — нет.

## Перед отправкой влить main и посмотреть diff глазами

Ветка, заведённая от устаревшего `main`, показывает в pull request **удаление чужих файлов**, и проверка базы этого не ловит: она считает удаления относительно того `main`, который был на момент её прогона, и отвечает «удалений нет». 01-10-2026 два открытых pull request в теме `training-dynamics` в таком виде снесли бы чужой разбор статьи и четырнадцать рисунков.

```bash
git fetch --all --prune
git merge --no-edit main          # merge, не rebase
git diff --stat main..HEAD        # смотреть глазами
```

Почему `merge`, а не `rebase`: rebase переписывает хеши, push отклоняется как non-fast-forward, и дальше тянет к `--force-with-lease` — ровно тем способом, которым 30-09-2026 уже были снесены выкладки с ветки. Если история всё же переписана, безопасный путь — пересобрать ветку поверх `origin/<ветка>` и перенести коммит `cherry-pick` **без флага `-q`**, чтобы молчаливый отказ был виден.

Относительные ссылки проверять не на глаз, а от каталога самого файла: из `<работа>/claims/<КОД>/README.md` до корня три уровня, из `<работа>/claims/<КОД>/theory/` четыре. Ошибка на один уровень проверку дерева не ломает, но ссылка не открывается.

## Чего не делать

Не править страницу темы вручную в обход `lab_page_sync.py`: разметка таблиц и формулы в них
чувствительны, а скрипт уже знает про грабли. Сырая вертикальная черта из формулы вроде
`||G||` рвёт строку таблицы, `$$` в ячейке не рендерится, обрезка текста оставляет непарный `$`,
а свои макросы статей (`\vtheta`) KaTeX не знает.

Не заводить второй репозиторий под литературу: она лежит в репозиториях тем, по одному на тему.

Не считать шаг выполненным по коду ответа. Проверять надо содержимое: страница открыта, разделы
на месте, файл рисунка существует по тому пути, на который ссылается разметка.
